# "나를 기다리는 세션"부터 한눈에 보이게 하라

> 조사 기준일: 2026-11-19. 근거는 `docs/research/notes/`의 노트 8개이고, Aquila Agents 현재 코드(`electron/hooks.ts`, `src/entities/session/ui/TerminalView.tsx`, `package.json`)를 직접 확인한 내용을 보탰다. 출처 없는 판단은 **[추론]**, 근거가 약한 예측은 **[추측]**으로 표시했다. 경쟁사가 쓴 비교 글(Paradev/Superset, crystl, Nimbalyst, Enjoy, Builder.io 등)은 따로 표시했다. Reddit 원문 스레드는 검색에 거의 걸리지 않아 사용자 목소리는 HN, GitHub 이슈, 포럼, 블로그에서 가져왔다.

사용자 입장에서 Aquila Agents를 가장 크게 개선하는 방법은 기능을 더 얹는 것이 아니다. **"지금 어느 세션이 나를 기다리는가"를 빠르고 정확하게, 맥락과 함께 보여 주는 것**이다. 여러 에이전트를 돌리는 사용자들은 맞는 탭을 찾는 데 하루 15~20분을 잃는다고 말하고, cmux·Warp·Paradev·Claude Code 데스크톱은 모두 이 문제를 핵심 기능으로 내세운다. 그런데 Aquila Agents의 상태 판정은 현재 `Notification` hook에 기대고 있어서 권한 프롬프트를 6~8초 늦게 잡는다. API 오류로 멈춘 세션은 "done"으로 보인다. 두 번째 축은 **신뢰**다. 재시작해도 세션이 돌아와야 하고, 한글 입력이 깨지지 않아야 하며, 세션이 15개여도 배터리와 GPU가 버텨야 한다. 코드를 보면 지금은 세션마다 WebGL 컨텍스트를 하나씩 만드는데, Chromium의 활성 컨텍스트 한도인 약 16개에 곧 닿는 구조다. 세 번째 축은 **Aquila Agents만의 자리**다. 1st-party 앱(Claude Code 데스크톱, Codex 앱)과 겹치는 시대에 Aquila Agents가 지킬 자리는 "진짜 CLI 그대로, 기존 체크아웃 그대로, 로그인 없이, Claude와 Codex를 한 화면에서"다. 그 위에 Figma 사용자를 위한 선택형 MCP 배선, 앱 내 프리뷰, 트렌드 버튼을 얹으면 차별점이 된다. 여기에 오너가 새로 요구한 **Windows 지원**이 우선순위를 바꾼다. Claude Code와 Codex는 둘 다 네이티브 Windows를 공식 지원하는데, Conductor·cmux·Superset은 Windows 빌드가 없다. 시장은 비어 있지만, 지금 코드의 `$SHELL -l -i -c` 실행, `curl` command hook, ⌘ 단축키, macOS 전용 시스템 명령은 그대로 옮겨지지 않는다. 그래서 **플랫폼 계층(셸 프로필·spawn 템플릿·경로·단축키)과 `http` 타입 hook 전환은 macOS 전용 코드를 더 늘리는 기능보다 먼저** 해야 한다. 오너 요구 사항이 두 가지 더 있다. 기능마다 스크린샷·짧은 애니메이션·단축키를 보여 주는 **앱 내 가이드(? 버튼)**와, 업데이트 후 첫 실행에 한 번 뜨는 **릴리즈 노트 모달**이다. 둘은 같은 모달 컴포넌트를 쓰고, 화면은 smoke 스크린샷 단계를 확장해 자동으로 찍는다. 아래 각 절은 이 축들을 기능 영역별로 풀고, 원격 머신 세션(프로젝트를 이 Mac 또는 SSH 서버에서 실행)도 오너 요구로 넣었다. 원격 tmux로 세션을 붙잡아 두고, 상태는 OSC 신호로 터미널 안에서 받는 구조다. 마지막에 T4–T12와 연결한 실행 로드맵을 둔다.

## 사용자가 래퍼를 떠나는 다섯 가지 이유는 Aquila Agents의 설계 원칙과 정확히 겹친다

래퍼 앱을 떠난 사용자들의 이유는 다섯 가지로 모인다. 진짜 CLI의 느낌과 키바인딩을 잃는다. 워크트리를 강제하면 `.env`와 PATH가 사라진다. GitHub 권한을 요구하고 재클론한다. Electron/Tauri가 느리다. 유지보수가 멈춘다. Conductor Show HN에서 aantix는 "The key bindings should be exactly the same… Sadly, this is lost with conductor"라고 썼다. _1tem은 "I wanted a simple git worktree manager for my existing, already-checked-out repository"라며 실망했다 ([HN Conductor](https://news.ycombinator.com/item?id=44594584)). vanja.io는 Claude Code 데스크톱 프리뷰를 써 본 뒤 gitignored 파일이 없어 DB 연결이 깨지는 "Worktree From Hell"을 겪었고, "Terminal + Opus. Not even close"라는 결론으로 터미널에 돌아갔다 ([vanja.io](https://vanja.io/claude-code-gui-vs-terminal-a-tale-of-two-workflows/)). cmux 저자는 기존 도구 "most of them were Electron/Tauri apps and the performance bugged me"를 제작 동기로 꼽았고, 그 결과 **28.8k stars**를 모았다 ([cmux README](https://github.com/manaflow-ai/cmux)). 시장 상황도 같은 방향을 가리킨다. Conductor는 Meta에 합류한 뒤 신규 가입을 닫았고(경쟁사 보도), Vibe Kanban 운영사는 문을 닫았으며, Crystal은 deprecated됐다 ([augmentcode](https://www.augmentcode.com/tools/open-source-agent-orchestrators), [DEV: Vibe Kanban alternatives](https://dev.to/agentverateam/vibe-kanban-alternatives-after-the-bloop-shutdown-2026-p80)). 사용자는 "버려지지 않을 가벼운 도구"를 찾고 있다.

Aquila Agents의 "pty에 진짜 CLI 임베드, 사용자 설정 무수정" 원칙은 이 불만들의 정반대에 서 있다. 그러니 원칙을 지키는 것 자체가 기능이다. 그러려면 첫 실행부터 깨지지 않아야 한다. macOS GUI 앱은 Finder나 Dock에서 실행되면 launchd의 최소 PATH만 받는다. 그래서 `claude`/`codex`를 못 찾는 것이 가장 확실한 첫 실패 지점이고, 표준 해법은 로그인 셸에서 PATH를 읽어 오는 `fix-path` 계열이다 ([fix-path](https://openapps.pro/packages/fix-path), [flaviocopes](https://flaviocopes.com/macos-app-command-line-tools-path.md)). Claude 공식 데스크톱 앱조차 셸 PATH 미적용 이슈가 있었다 ([#42248](https://claudeissues.com/issue/42248-desktop-app-macos-ignores-path-from-all-sources-read-tool-cannot-find-poppler-pd)). 패키지 빌드에서 fix-path가 안 먹혔다는 보고도 있다 ([fix-path #11](https://github.com/sindresorhus/fix-path/issues/11)). 따라서 T8 패키징의 완료 조건에 "Finder에서 실행해 `claude --version` 감지 성공"을 넣고, 실패하면 바이너리 경로를 직접 지정하는 탈출구를 두어야 한다 ([paseo troubleshooting](https://paseo.sh/docs/troubleshooting.md)). Windows에서는 문제의 모양이 다르다. 네이티브 Claude Code는 `%USERPROFILE%\.local\bin\claude.exe`에 설치되고, WSL 안에 설치한 `claude`는 Windows 쪽 PATH에 보이지 않는다 ([Claude Code setup](https://code.claude.com/docs/en/setup)). 그래서 감지 체크리스트가 "네이티브 / WSL 배포판별"로 나뉘어야 한다(아래 Windows 절). 강제 로그인과 설문은 Warp가 2024년에 철회할 만큼 반발이 컸다 ("why do I need an account to use a terminal app?" — [itsfoss](https://itsfoss.com/news/warp-terminal-no-login/)). Crystal은 "no custom config files I have to think about"이라는 이유로 선택받았다 ([HN](https://news.ycombinator.com/item?id=44594584)). **[추론]** 첫 실행 화면은 다섯 단계면 충분하다. PATH 복원, `claude`/`codex`/`git` 감지 체크리스트(없으면 설치 명령 복사), "폴더 추가"(드래그앤드롭), 로그인은 CLI 안에서 하라는 안내, 단축키 힌트가 붙은 빈 상태다. Figma 연결 같은 선택 항목은 "건너뛰기"를 기본으로 둔다.

macOS 완성도에서 사용자가 실제로 언급하는 것은 빠른 시작, 낮은 메모리, 전역 핫키 창, 자동 업데이트, 접근성이다 ([cmux README](https://github.com/manaflow-ai/cmux), [Ghostty features](https://ghostty.org/docs/features)). 한국어 사용자에게는 IME 안정성이 이 모두보다 앞선다. Claude Code CLI에는 한글 자모 분리, 스페이스 입력 시 마지막 음절 소실, 한글 상태에서 Ctrl 단축키 무시, 조합 중 글자 미표시 이슈가 줄줄이 쌓여 있다. 2026년 8~9월 macOS 보고의 제목은 "macOS Korean Hangul IME composition is a daily usability blocker"였다 ([#87869](https://claudeissues.com/issue/87869-macos-korean-hangul-ime-composition-is-a-daily-usability-blocker-for-cli-real-ti), [#62969](https://claudeissues.com/issue/62969-bug-korean-hangul-ime-last-syllable-dropped-on-space-punctuation-in-input), [#40291](https://claudeissues.com/issue/40291-korean-ime-all-ctrl-key-shortcuts-silently-ignored-when-hangul-input-is-active)). 호스트도 원인이 될 수 있다. libghostty 기반 cmux에서도 한글 조합이 깨졌다 ([#37419](https://claudeissues.com/issue/37419-cmux-korean-ime-composition-broken-jamo-separated-after-fn-key-press)). Electron+xterm.js인 Wave Terminal에서도 CJK 조합이 깨졌는데, 보고자는 같은 조합인 VS Code 터미널은 정상이라며 원인을 앱의 입력 처리 계층으로 지목했다 ([waveterm #2915](https://gh.r-mj.com/wavetermdev/waveterm/issues/2915)). 즉 고칠 수 있는 영역이다. **[추론]** VS Code의 xterm.js 통합 방식을 기준으로 한글 IME 회귀 체크리스트를 만들고 smoke에 넣는다. 항목은 자모 분해, 중복 입력, 조합 중 표시, 조합 중 Enter/Space, 한/영 전환 직후 Ctrl·⌘ 단축키다. 선택 기능으로 "호스트 측 멀티라인 입력창에서 조합을 끝낸 뒤 한 번에 붙여넣기"를 두면 IME 문제와 멀티라인 입력 문제를 함께 완화할 수 있다(검증 필요). CLI raw-mode 쪽 버그는 남는다.

## 상태 판정을 6~8초 앞당기고 거짓 "done"을 없애는 것이 가장 싼 고효과 개선이다

멀티 에이전트 사용자의 최대 비용은 주의력이다. Product Hunt 토론 참가자들은 "맞는 pane을 찾고 나면 20분이 지나 있다"고 했고, 손실을 **하루 15~20분**, 전환 후 재진입에 다시 5~10분으로 추정했다. 소리 알림은 헤드폰을 쓰거나 깊이 집중하면 묻히고, 에이전트별 차임은 4개를 넘으면 한계라고 했다 ([Product Hunt](https://www.producthunt.com/p/vibecoding/your-ai-agent-is-waiting-for-you-your-attention-isn-t-how-much-time-do-you-lose-to-this)). cmux가 생긴 이유도 같다. Claude Code 알림 본문이 항상 "Claude is waiting for your input"이라 맥락이 없었다 ([cmux README](https://github.com/manaflow-ai/cmux)). 업계 상태 모델은 이미 수렴했다. Claude Code agent view는 Working / Needs input / Idle / Completed / Failed / Stopped의 6종을 쓰고, JSON 상태는 `working|blocked|done|failed|stopped`다 ([agent view](https://code.claude.com/docs/en/agent-view)). Aquila Agents의 waiting > error > working > done > idle 우선순위는 이 모델과 맞는다. 다만 **[추론]** Ctrl+C로 끝낸 세션을 빨강 error로 보이면 오탐이 되므로, "stopped"를 error와 분리해야 한다.

판정 엔진에는 실제 결함이 있다. 현재 `electron/hooks.ts`는 `UserPromptSubmit`→working, `PostToolUse`→working, `Notification`→waiting, `Stop`→done의 4개 이벤트만 주입하고, 각 hook은 `curl`을 부르는 command 타입이다. 이 방식은 Windows에서 깨지기 쉬우므로 모든 플랫폼에서 `http` 타입으로 바꾸는 편이 낫다(아래 Windows 절). 그런데 공식 문서에 따르면 `permission_prompt` Notification은 **사용자가 약 6초간 타이핑하지 않아야** 발화하고, 키를 누를 때마다 연기된다 ([hooks docs](https://code.claude.com/docs/en/hooks)). 실제로는 약 8초 뒤에 발화한다는 보고와 thinking 중에는 아예 발화하지 않는 회귀(2.1.141) 보고도 있다 ([#43530](https://claudeissues.com/issue/43530-notification-hook-fires-8-seconds-after-permission-prompt-appears), [#58909](https://claudeissues.com/issue/58909-2-1-141-notification-permission-prompt-hook-event-stops-firing-during-active-thi)). 해법은 이미 hook 목록에 있다. **`PermissionRequest`** hook은 권한 다이얼로그가 뜨는 시점에 발화하고, decision을 돌려주지 않으면 원래 프롬프트가 그대로 진행된다. 그러니 exit 0으로 waiting만 보고하면 된다. **`StopFailure`**는 `rate_limit`, `authentication_failed`, `billing_error`, `server_error` 같은 matcher로 API 오류 종료를 알린다 ([hooks docs](https://code.claude.com/docs/en/hooks)). 지금은 프로세스 비정상 종료만 error로 잡으므로, rate limit으로 멈춘 세션이 초록 "done"으로 보이는 거짓 완료가 생긴다. **[추론]** `PermissionDenied`·`PostToolUse`·`UserPromptSubmit`이 오면 waiting을 해제하고, Esc 취소처럼 hook이 없는 경우를 위해 "그 세션에 키 입력이 들어오면 waiting 해제"라는 보조 규칙을 둔다. `idle_prompt`는 waiting 트리거로 쓰지 않는다. 60초 하드코딩, 서브에이전트 실행 중 오발화, 미발화 보고가 모두 있다 ([#13922](https://claudeissues.com/issue/13922-feature-configurable-timeout-for-idle-prompt-notification-hook), [#93672](https://claudeissues.com/issue/93672-bug-notification-idle-prompt-fires-while-background-subagents-are-still-running)). `SubagentStart`/`SubagentStop` 카운트로 "Stop이 왔지만 서브에이전트가 도는 중"을 working으로 유지하는 방안도 검토할 만하다.

장기적으로 더 견고한 경로도 열렸다. **OSC 7501 Program Status Protocol**은 Ghostty의 Mitchell Hashimoto가 2026-10에 제안한 터미널 시퀀스로, 프로그램이 idle/working/blocked(사용자 대기)/done/error 상태를 직접 보고한다 ([control-codes spec](https://control-codes.page/proposals/osc-7501/)). Claude Code는 **v2.1.295(2026-10-08)부터 이를 내보낸다** ([CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). xterm.js `parser.registerOscHandler(7501, …)`로 받으면 hook 주입 없이 상태를 얻으므로 규칙 6과 가장 잘 맞는다. 다만 아직 제안 단계(rev 0.4)이고 날짜 표기도 출처마다 엇갈린다. Claude의 OSC 제목·진행률 신호는 형식이 자주 바뀌어 이를 쓰던 herdr와 Warp 통합이 깨진 전례가 있다 ([#68643](https://claudeissues.com/issue/68643-osc-title-not-emitting-idle-marker-after-turn-ends-breaks-herdr-status-detection), [warp#10715](https://upd.dev/warpdotdev/warp/issues/10715)). 그러니 hook을 주 경로로 유지하고 OSC 7501을 교차 검증 신호로 병행하는 것이 안전하다(**검증 필요**). (2026-11-19 확인으로 이 판단을 바꿨다. Claude Code는 터미널이 질의에 응답할 때만 OSC 7501을 쓰고, Codex 0.169.1도 같은 시퀀스를 내보낸다. 아래 [구현 전 확인 결과](#구현-전-확인-결과-2026-11-19)의 권고 참조.) Codex 쪽 사정도 달라졌다. 2026년에 hook 14종(PermissionRequest, Stop, Interrupt 등)이 정식화돼, 이제 3초 출력 휴리스틱 없이도 결정적 판정이 가능하다 ([Codex hooks](https://learn.chatgpt.com/docs/hooks)). 관건은 `~/.codex`를 건드리지 않는 주입이다. 후보는 두 가지다. 하나는 `codex -c tui.notifications=true -c tui.notification_method="osc9" -c tui.notification_condition="always"`로 TUI 알림을 OSC 9로 내보내게 하고 xterm.js에서 가로채는 방식으로, approval-requested까지 잡힌다 ([Vaughan](https://codex.danielvaughan.com/2026/04/13/codex-cli-notification-pipeline-osc9-hooks-alerts/)). 다른 하나는 `-c`로 `[hooks]`를 인라인 주입하는 방식이다. 둘 다 `-c` 동작, OSC 9 본문 형식, `/hooks` 신뢰 승인 절차와의 관계를 **구현 전에 검증해야 한다**. (2026-11-19 로컬 확인: `-c key=value` 오버라이드는 동작한다. 노트의 `tui.focused_notifications` 키는 바이너리에 없고 `tui.notification_condition="always"`가 맞다. 인라인 hooks는 `trust_hooks` 신뢰 절차 때문에 사용자 조치 없이는 어렵다고 본다.) 휴리스틱으로 얻은 done은 흐린 초록 같은 "추정" 표시로 비용을 낮춘다.

판정이 정확해지면 표시 방식이 가치를 만든다. 검증된 패턴은 다섯 가지다. 대기 수 상시 노출(Paradev 독 배지, Claude 탭 제목 "2 awaiting input"), 받은편지함(Warp mailbox의 All/Unread/Errors, 탭에 들어가면 자동 읽음), 대기 세션 단축 이동(cmux ⌘⇧U), 클릭하면 정확한 세션으로 점프하는 알림, 맥락을 담은 알림 본문이다 ([Paradev docs](https://docs.paradev.com/agent-status), [Warp docs](https://docs.warp.dev/agents/capabilities/agent-notifications/), [cmux docs](https://cmux.com/docs/notifications)). 독 배지는 macOS 전용이다. **[추론]** Windows에서는 작업 표시줄 `win.setOverlayIcon()`(대기 수)과 `win.flashFrame(true)`(입력 대기)가 대응물이다(검증 필요). 특히 "다음 대기 세션으로 점프"는 Claude agent view 문서에도 전용 단축키가 없다 ([agent view](https://code.claude.com/docs/en/agent-view)). Aquila Agents처럼 프로젝트를 가로지르는 앱이 차별화할 수 있는 지점이다. 알림 본문에는 프로젝트명, 탭 이름, `Stop`이 주는 `last_assistant_message` 첫 줄, waiting이면 `PermissionRequest`의 `tool_name`/`tool_input` 요약(예: "Bash: npm install")을 넣는다. Notification 페이로드에는 대기 중인 도구 정보가 없다는 불만이 이슈로 올라와 있다 ([#84801](https://claudeissues.com/issue/84801-feature-richer-permission-prompt-notifications-sharing-a-workaround-ref-32952-29)). 사용자 요구 1순위인 억제 규칙("세션이 이미 보이면 알리지 말 것")은 이미 구현돼 있다 ([#53194](https://claudeissues.com/issue/53194-feature-dont-trigger-system-notifications-when-the-claude-code-session-is-alread)). 여기에 같은 상태 디바운스, yolo 세션은 done만 알리기([#30233](https://claudeissues.com/issue/30233-bug-notifications-should-not-fire-in-auto-accept-yolo-mode-sessions)), "12분째 대기" 경과 시간과 1회 리마인드를 더한다. 알림 버튼에서 바로 승인하는 기능은 수요가 있지만([#62458](https://claudeissues.com/issue/62458-feature-request-actionable-approve-deny-on-mobile-push-for-permission-prompts)) **[추론]** pty에 키를 보내는 오승인 위험과 "CLI 재구현 금지" 원칙 때문에 후순위다. "클릭 → 해당 세션으로 이동"이 먼저다.

## 복원은 ID로 resume하고, 실패하면 스크롤백으로 받쳐야 한다

세션 관리에서 사용자가 일관되게 원하는 것은 두 가지다. 재시작 후 **내용과 살아 있는 세션까지** 돌아오는 것, 그리고 탭이 많을 때도 길을 잃지 않는 것이다. Ghostty가 레이아웃만 복원하자 사용자들은 "iTerm2와 Apple Terminal은 수년간 제공해 왔고, 많은 사용자가 기본 기능으로 여긴다"고 반박했다 ([Ghostty #12912](https://github.com/ghostty-org/ghostty/discussions/12912), [HN 50261998](https://news.ycombinator.com/item?id=50261998)). 복원 기대치는 세 단계로 정리된다. ① 레이아웃+cwd, ② 스크롤백, ③ 살아 있는 세션 재개다. T4의 `claude --resume`/`codex resume` 계획은 ③에 해당한다. 문제는 resume picker 자체가 버그투성이라는 점이다. picker가 비어 보이고, 2.1.104에서는 범위가 현재 디렉터리로 한정되지 않는 회귀가 있었다. worktree 안에서는 0행으로 접히고, 동명 세션을 구분할 수 없고, 엉뚱한 세션이 로드되기도 한다. 공통 우회책은 picker를 건너뛰고 `claude -r <uuid>`로 jsonl을 직접 읽는 것이다 ([#25685](https://claudeissues.com/issue/25685-session-resume-picker-shows-no-sessions-sessions-index-json-stops-updating), [#51658](https://claudeissues.com/issue/51658-bug-resume-picker-no-longer-scoped-to-current-directory-regression-in-2-1-104), [#86633](https://claudeissues.com/issue/86633-bug-in-session-resume-picker-collapses-to-0-rows-inside-a-git-worktree-and-never), [cybersader](https://cybersader.github.io/agentic-workflow-and-tech-stack/stack/patterns/claude-code-session-recovery/)). 그러므로 T4는 **스폰 시점에 hook 페이로드의 `session_id`를 포착해 저장하고 ID로 resume**해야 한다. Paradev(Electron+xterm.js)는 같은 문제를 겪고 두 가지 교훈을 남겼다. 비정상 종료를 감지하면 이전 출력을 읽기 전용으로 보여 주고 같은 디렉터리에서 새 셸을 여는 **cold restore**, 그리고 10 pane을 한꺼번에 열 때 spawn storm을 피하려고 **활성 터미널부터 hydrate**하는 방식이다 ([Paradev daemon deep dive](https://paradev.com/cs/blog/terminal-daemon-deep-dive), 자사 글). **[추론]** Aquila Agents도 마지막 스크롤백을 `~/.aquila/`에 저장해 resume 실패 시의 fallback으로 쓰고, 백그라운드 탭은 클릭할 때 resume하는 지연 spawn을 기본으로 두는 것이 맞다. pty를 main 프로세스가 소유하므로 앱 업데이트나 크래시 때 세션이 죽는 문제는 남는다. Paradev는 이를 별도 터미널 데몬으로 풀었는데, Aquila Agents에는 장기 과제다.

키보드에서는 증거가 가장 구체적인 패턴부터 넣는다. cmux HN 사용자들은 커맨드 팔레트, 단축키 재정의, ⌘Z pane zoom을 요청했다 ([cmux blog](https://cmux.com/blog/show-hn-launch)). Claude Code 데스크톱은 **⌘/로 단축키 전체 목록**을 띄우고, 사이드바를 상태·프로젝트별로 필터하며, PR이 머지되면 세션을 자동 보관해 "사이드바가 살아 있는 것에 집중"하게 한다 ([Anthropic: desktop redesign](https://claude.com/resources/articles/claude-code-desktop-redesign)). zellij는 상태바에 가능한 키를 보여 줘 "암기 부담을 없앴다"는 평을 받는다 ([Zellij 리뷰](https://jpk-io.pages.dev/dev-tools/zellij-terminal-multiplexer-review/)). **[추론]** T6의 ⌘K는 명령 실행기에 그치지 않고 **세션 퀵 스위처**를 겸해야 한다. 프로젝트명, 탭 이름, 상태("waiting")로 퍼지 검색하고, 각 항목 옆에 단축키를 표시해 학습을 돕는다. 표기는 플랫폼별로 달라야 한다. Windows에서 ⌘를 Ctrl로 단순 치환하면 터미널의 Ctrl+C/V/W/T와 정면으로 충돌하므로, Windows Terminal처럼 Ctrl+Shift 계열을 쓴다(아래 Windows 절). 고정 1/2 분할에는 저비용 보완 두 가지가 있다. WezTerm `TogglePaneZoomState`처럼 한 pane을 잠깐 키웠다 되돌리는 **pane zoom 토글**과 키보드 리사이즈다. 긴 Claude 출력을 읽는 상황에 정확히 맞는다 ([WezTerm docs](https://wezterm.org/config/lua/keyassignment/TogglePaneZoomState.html)). iTerm2식 broadcast input은 에이전트 맥락의 수요 근거를 찾지 못했으므로 후순위다.

터미널 본연의 품질에서는 호스트가 고칠 수 있는 작은 것들이 체감을 좌우한다. Codex 사용자들의 최다 불만은 텍스트 Ctrl+V가 "no image on clipboard"로 실패하는 것과 클립보드 이미지를 바로 붙일 수 없는 것이다 ([codex #44323](https://github.com/openai/codex/issues/44323), [#6080](https://github.com/openai/codex/issues/6080)). 2026-10의 #53380은 "Codex CLI terminal UX has regressed badly"라며 스크롤백·선택·복사의 불편을 지적했다 ([#53380](https://github.com/openai/codex/issues/53380)). Claude Code의 깜빡임과 스크롤 점프는 2025~2026년 내내 반복 보고됐다 ([#769](https://github.com/anthropics/claude-code/issues/769), [#18299](https://github.com/anthropics/claude-code/issues/18299)). **[추론]** Aquila Agents가 직접 할 수 있는 보조 기능은 네 가지다. ⌘V 시 클립보드가 이미지면 임시 파일로 저장하고 경로를 입력하기(드래그앤드롭도 같은 방식), "마지막 응답 복사", 위로 스크롤하면 자동 스크롤을 멈추고 "맨 아래로" 버튼 보여 주기, Kitty hints나 WezTerm QuickSelect식 키보드 URL·경로 선택이다. QuickSelect류는 "Kitty에서 Ghostty로 옮기지 못하는 유일한 이유"로 꼽힐 만큼 충성도가 높다 ([HN 50261998](https://news.ycombinator.com/item?id=50261998)).

## 병렬 에이전트의 진짜 문제는 런타임 격리와 사람의 리뷰 용량이다

워크트리는 파일 격리만 해결한다. 포트, DB, Docker, `.env`, node_modules 같은 런타임 격리는 해결하지 않는다. 이것이 모든 제품의 공통 불만 1순위다. "Git worktrees solve filesystem isolation but not runtime isolation"이라는 문장 그대로 세 에이전트가 3000 포트를 두고 싸운다 ([DEV](https://dev.to/gabrielanhaia/git-worktrees-for-coding-agents-break-on-env-nodemodules-and-port-3000-fix-all-three-3781)). Superset Launch HN의 toddmorey는 "I've never used lsof so much in my life"라고 했다 ([Launch HN: Superset](https://news.ycombinator.com/item?id=48236770)). 잘 된 제품들의 답은 같다. 레포별 setup/teardown 스크립트, gitignored 파일 복사 규칙, 워크스페이스별 포트 블록이다. Superset은 `SUPERSET_PORT_BASE`로 **연속 20개 포트 블록**을 예약하고, teardown 때 포트와 컨테이너를 정리한다 ([Superset README](https://github.com/superset-sh/superset/blob/main/README.md)). Claude Code는 `.worktreeinclude`(gitignore 문법)로 `.env` 같은 gitignored 파일을 복사한다. 깨끗한 워크트리는 자동 삭제하고, 변경이 있으면 keep/remove를 묻고, 머지가 감지되면 같은 이름을 재사용할 때 리셋한다 ([Claude Code docs: worktrees](https://code.claude.com/docs/en/worktrees.md)). T7에는 함정이 하나 있다. 계획된 `../<repo>-wt/<branch>` 위치는 Claude Code 기본 위치(`.claude/worktrees/`)와 다르다. **[추론]** 사용자가 `claude --worktree`와 섞어 쓰면 워크트리가 두 곳에 흩어진다. 그러니 어디서 만들었든 `git worktree list`를 읽어 사이드바에 보여 주고, 복사 규칙은 별도 포맷을 새로 만들지 말고 `.worktreeinclude`를 재사용해야 사용자 부담이 적다. 처음 보는 디렉터리에서는 workspace trust 대화상자를 통과해야 `--worktree`가 동작한다는 점도 안내해야 한다.

워크트리를 강제해서는 안 된다는 증거도 분명하다. Claude 데스크톱 앱이 새 세션마다 워크트리를 만들고 끌 토글이 없다는 불만이 이슈로 올라와 있다 ([#91472](https://claudeissues.com/issue/91472-feature-make-git-worktree-pooling-opt-out-one-worktree-per-session-removed-only)). Conductor 사용자도 "main 브랜치에서 작업하는 세션도 원한다"고 했다 ([HN 46029331](https://news.ycombinator.com/item?id=46029331)). 병렬화 자체에 대한 회의도 크다. koliber는 "the limiting factor is my attention"이라며 3개 이상은 무의미하다고 했고, bob1029는 "One 'slow' agent can outpace many fast ones"라고 했다 ([Ask HN](https://news.ycombinator.com/item?id=46682551)). 2026-11-17 HN 319점을 받은 하버드 연구도 병목이 코드 리뷰로 옮겨 갔다고 보고했다 ([ComplexDiscovery](https://complexdiscovery.com/harvard-researchers-find-ai-coding-agents-shifted-the-bottleneck-to-code-review/)). 비용도 선형으로 는다. 백그라운드 세션도 구독 쿼터를 똑같이 소모하므로 Pro 5시간 창은 병렬 5개면 1시간 안에 소진될 수 있다 ([CloudZero](https://www.cloudzero.com/blog/claude-code-agents/)). 결론적으로 Aquila Agents가 투자할 곳은 "더 많은 병렬"이 아니다. 주의 관리(앞 절), 런타임 격리, 리뷰(다음 절)다. **[추론]** 프로젝트 설정 화면(T5)에 기본 에이전트, 기본 브랜치, setup 스크립트, 포트 베이스, "Open in" 에디터를 두고, 시스템 모니터(T12)에 **세션별 리스닝 포트**를 cmux처럼 표시하면 `lsof` 문제를 직접 해결할 수 있다.

계정 쪽에서 Aquila Agents의 shared(`~/.claude`)/personal(`CLAUDE_CONFIG_DIR`) 설계는 커뮤니티 표준과 일치한다. 주의할 점이 하나 있다. `CLAUDE_CONFIG_DIR=~/.claude`를 명시하면 기본 `claude`와 **별도의 macOS Keychain 항목**이 생긴다 ([enjoy.dev](https://enjoy.dev/blog/multiple-claude-code-accounts/), 판매사 글). 그러니 shared 계정은 변수를 비워 두는지 코드에서 점검해야 한다. Windows에는 이 Keychain 문제가 없다. 자격 증명이 `%USERPROFILE%\.claude\.credentials.json` 파일이고, `CLAUDE_CONFIG_DIR`을 주면 그 디렉터리 아래에 저장된다 ([Claude Code authentication](https://code.claude.com/docs/en/authentication)). 사용자가 가장 원하는 차별 기능은 **계정별 5시간·주간 사용량 막대를 나란히, 리셋 시각과 함께** 보여 주는 것이다. Claude Code의 statusline `rate_limits`는 계정이 다른 동시 세션 사이에서 섞여 보이는 버그가 보고됐으므로, 세션별이 아니라 계정 디렉터리별로 조회해야 한다 ([#68772](https://claudeissues.com/issue/68772-bug-concurrent-sessions-on-different-accounts-share-rate-limit-display-statuslin)). 한도 근처에서 자동으로 계정을 바꾸는 기능은 수요가 있지만 약관 회색지대와 토큰 복사 위험이 있다. **[추론]** "한도 임박 알림 + 다른 계정으로 새 세션 열기" 버튼까지가 적절하다.

## 리뷰 루프와 히스토리는 CLI picker의 빈틈을 정확히 메울 수 있다

2026년의 표준 리뷰 루프는 diff 보기 → 줄 코멘트 → 코멘트를 묶어 에이전트에 보내기 → 새 diff 재검토 → hunk·파일 단위 stage/revert → 커밋·PR이다. Claude Code 데스크톱은 줄을 클릭해 코멘트를 모은 뒤 ⌘Enter로 한 번에 보낸다 ([Desktop docs](https://code.claude.com/docs/en/desktop)). Codex 앱은 전체·파일·hunk 3단계 stage/revert를 지원한다 ([Codex app: Review](https://developers.openai.com/codex/app/review)). 이 영역의 불만은 대부분 리뷰 UI가 실제 git 상태와 어긋날 때 생긴다. Cursor의 리뷰 목록은 stale 파일이 쌓이고, 셸로 쓴 변경은 아예 빠진다 ([Cursor forum: stale](https://forum.cursor.com/t/ai-agent-file-review-list-accumulates-stale-files-and-doesnt-sync-with-git-status/145914), [terminal edits missing](https://forum.cursor.com/t/agent-edits-made-via-the-terminal-script-shell-writes-dont-appear-in-the-inline-edit-review-ui/162348)). Claude 데스크톱에서는 인라인 코멘트가 카드로 보이는데 실제로 전달되지 않는 버그가 있었다 ([#96597](https://claudeissues.com/issue/96597-bug-projects-beta-inline-changes-comments-do-not-reach-their-thread)). git 상태를 직접 읽는 Aquila Agents의 읽기 전용 Changes 패널은 이 문제를 구조적으로 피한다. **[추론]** 이 장점을 "git working tree 기준 · 마지막 갱신 n초 전"으로 드러내고, 다음 순서로 확장한다. 먼저 unified/side-by-side 전환과 j/k 파일 내비게이션을 넣는다. 다음으로 줄 코멘트를 `파일:줄` + 코드 인용 + 코멘트 형태의 프롬프트로 만들어 **활성 세션 입력창에 붙여넣고, 전송은 사용자가** 하게 한다. 채팅 재구현 없이 루프를 닫는 방법이다. Codex 문서는 코멘트를 "리뷰 가이드"로 취급하므로 의도를 적은 한 줄을 덧붙이라고 권한다. 그다음 확인창이나 stash 백업이 있는 hunk stage/revert, 마지막으로 에이전트에게 커밋 메시지나 PR 설명을 요청하는 프롬프트 주입 버튼이다. Claude 체크포인트는 Bash로 바뀐 파일을 추적하지 않으므로 ([Checkpointing docs](https://code.claude.com/docs/en/checkpointing)), "세션 시작 시점 대비 diff"(시작할 때 HEAD를 기록)는 Aquila Agents만의 차별점이 될 수 있다.

세션 히스토리(T11)는 수요가 이미 증명된 공백이다. Claude Code는 `/rename` 이름이 picker에 안 나오고, 이름으로 검색되지 않으며, 디스크에 멀쩡한 transcript가 목록에서 빠지기도 한다. picker에서 이름을 바꾸게 해 달라는 요청과 picker에 이름을 표시해 달라는 요청은 **not planned로 닫혔다** ([#25311](https://github.com/anthropics/claude-code/issues/25311), [#43963](https://github.com/anthropics/claude-code/issues/43963), [#96559](https://github.com/anthropics/claude-code/issues/96559), [#72895](https://github.com/anthropics/claude-code/issues/72895), [#39414](https://github.com/anthropics/claude-code/issues/39414)). Codex picker도 첫 메시지로만 필터한다 ([codex #10315](https://github.com/openai/codex/issues/10315)). 그 결과 jsonl 검색 CLI(Show HN search-sessions), 뷰어, VS Code 사이드바 같은 서드파티 생태계가 생겼다 ([HN search-sessions](https://news.ycombinator.com/item?id=47128630)). 게다가 transcript는 `cleanupPeriodDays` 기본 **30일** 뒤에 삭제된다 ([dev.to](https://dev.to/heylittlepan/claude-code-conversation-history-where-it-lives-how-to-search-it-how-to-get-it-back-4lc8)). **[추론]** T11 패널은 다음을 갖춰야 한다. 사용자 지정 이름(없으면 첫 메시지), 마지막 활동 시각, 브랜치/cwd, 세션 ID 복사를 표시한다. 이름·첫 메시지·본문 전체를 검색한다. 경로 인코딩 디렉터리명이 아니라 jsonl 안의 `cwd` 필드로 프로젝트를 묶는다. 재개는 반드시 ID로 한다. "30일 자동 삭제" 경고와 Markdown 내보내기를 둔다. 이름과 즐겨찾기는 규칙 6에 따라 `~/.aquila/` 쪽 메타데이터로 저장한다. Codex는 v0.145에서 SQLite 기반 히스토리로 바뀌었다는 서드파티 주장이 있었다 ([danielvaughan v0.145](https://codex.danielvaughan.com/2026/07/26/codex-cli-paginated-thread-history-sqlite-search-resume-persisted-names-memories/)). 2026-11-19 로컬 확인(codex-cli 0.169.1) 결과 `~/.codex/sessions/YYYY/…` jsonl rollout과 SQLite(`thread_history_1.sqlite`, `state_5.sqlite`, `sqlite/codex.db`), `session_index.jsonl`이 **함께** 있다. 히스토리 패널은 jsonl만 가정하면 안 되고, 두 저장소를 읽기 전용으로 다루는 어댑터를 둔다.

컨텍스트와 사용량에서 사용자가 원하는 것은 **항상 보이는 게이지**다. 기본 auto-compact 경고는 약 95% 근처에서야 뜨고 ([#15247](https://github.com/anthropics/claude-code/issues/15247)), 품질이 떨어지기 전인 약 60%에서 미리 compact하라는 권장이 퍼져 있다 ([mindstudio](https://www.mindstudio.ai/blog/claude-code-compact-command-context-management)). 컨텍스트 사용률을 자동으로 얻을 수 있는 곳은 statusline의 `context_window` 데이터(2.1.72+)뿐이다 ([claudecode.jp](https://claudecode.jp/en/news/student/claude-code-statusline-context-usage-display)). **[추론]** 이미 주입하는 `--settings` 파일에 statusline 명령을 넣어 이 JSON을 `~/.aquila/`에 기록하게 하면, 사용자 설정을 건드리지 않고 탭마다 작은 게이지를 띄울 수 있다. 다만 사용자가 자기 statusline을 쓰고 있다면 `--settings`가 그것을 덮는지 병합하는지 **검증해야 한다**. (2026-11-19 확인: 공식 설정 문서상 `--settings`는 user·project·local보다 위, managed보다 아래이고 같은 키는 덮어쓴다. `statusLine`은 단일 객체 키이므로 **사용자 statusline을 대체한다**. 반면 hook은 레벨 사이에서 병합된다 ([Settings precedence](https://code.claude.com/docs/en/settings#settings-precedence), [Hooks](https://code.claude.com/docs/en/hooks)). 그러니 사용자 `statusLine`이 있으면 주입하지 않는다.) 구독 사용자에게 진짜 관심사는 달러가 아니라 "5시간 창과 주간 한도가 얼마 남았고 언제 리셋되나"다. `/usage`가 이를 보여 주지만 항상 보이지는 않아서 ccusage, 메뉴바 앱들이 널리 쓰인다 ([claudcod](https://claudcod.com/blog/claude-code-rate-limits/), [ccusage](https://github.com/processtrader/ccusage)). 정확한 한도는 비공개이므로 로컬 jsonl 합산값은 "추정"이라고 명시해야 한다. 메모리 지우기(T11)도 미리보기가 필요하다. auto memory는 MEMORY.md 앞 200줄/25KB만 로드되고 CLAUDE.md와 따로 관리되므로 ([aident](https://aident.ai/blog/audit-claude-code-auto-memory)), 지우기 전에 둘을 구분해 줄 수와 크기를 보여 주고 휴지통 이동 원칙을 지킨다.

## Figma 사용자에게는 "배선은 자동, 설정은 선택, 판단은 whoami"가 정답이다

2026년 말의 표준은 Figma 공식 **원격 MCP 서버 `https://mcp.figma.com/mcp`**(OAuth)다. Claude Code와 Codex 모두 desktop·remote·write-to-canvas를 지원하는 카탈로그 등재 클라이언트다 ([Figma Help: MCP guide](https://help.figma.com/hc/en-us/articles/32132100833559-Guide-to-the-Figma-MCP-server)). 따라서 Aquila Agents는 Figma 연동을 직접 구현할 필요가 없고, 공식 MCP를 세션에 꽂아 주는 배선과 UX만 맡으면 된다. Claude Code는 **`--mcp-config <file>` 플래그로 세션 단위 주입**이 된다. `--strict-mcp-config`를 붙이면 넘긴 서버만 로드한다 ([Claude Code Docs: MCP](https://code.claude.com/docs/en/mcp)). 그러니 `~/.aquila/mcp/figma.json`(`{"mcpServers":{"figma":{"type":"http","url":"https://mcp.figma.com/mcp"}}}`)을 만들고, Figma를 켠 프로젝트의 claude spawn에만 붙이면 된다. 기존 `--settings` 주입과 같은 패턴이다. 사용자의 기존 MCP를 지우지 않도록 `--strict`는 붙이지 않는다. 인증은 세션 안의 `/mcp`나 `claude mcp login figma`가 처리하는데, 이때 토큰은 Claude 관리 저장소(키체인 등)에 저장된다. Aquila Agents가 쓰는 것이 아니라 CLI의 동작이라는 점을 문서에 분명히 해 둔다. Codex는 `~/.codex/config.toml`과 신뢰된 프로젝트 `.codex/config.toml`만 문서화돼 있다 ([Codex MCP](https://developers.openai.com/codex/mcp)). `~/.codex` 쓰기는 규칙 위반이므로 남은 길은 두 가지다. 사용자 확인 후 repo의 `.codex/config.toml`에 추가하거나, `codex -c mcp_servers.figma.url=…` override가 되는지 검증하는 것이다(**검증 필요**. 2026-11-19 로컬 확인으로 `-c key=value`가 TOML로 파싱되어 `~/.codex/config.toml` 값을 덮는다는 점은 확인했다. `mcp_servers.*` 키를 실제로 받는지는 실측이 남았다). 설정 방식이 가이드마다 달라 혼란이 있고(transport 표기 sse/http), 조직이 플러그인 설치를 막으면 수동 추가가 필요하다 ([Griffin Wooldridge](https://griffinwooldridge.com/blog/figma-mcp-claude-code-setup)). 원클릭 배선이 사용자에게 주는 가치가 큰 이유다.

플랜과 시트 확인은 기능을 켜고 끄는 근거가 된다. 기능 가용성은 **파일이 속한 플랜 × 시트(View/Collab/Dev/Full)** 조합으로 정해진다. Pro Dev 시트 사용자가 Starter 한도에 걸린 사례가 그 증거다 ([Figma Forum 54926](https://forum.figma.com/report-a-problem-6/figma-mcp-server-stuck-on-starter-limits-despite-active-professional-dev-seat-54926)). 가장 확실한 자동 확인 수단은 원격 MCP의 **`whoami` 도구**다. 이메일, 소속 플랜, 플랜별 시트를 돌려주고 **rate limit에서 제외**된다. REST `GET /v1/me`는 플랜과 시트를 주지 않는다 ([Rate limits & access](https://developers.figma.com/docs/figma-mcp-server/rate-limits-access/), [Users endpoints](https://developers.figma.com/docs/rest-api/users-endpoints/)). **[추론]** "Figma 연결"을 누르면 OAuth 뒤에 숨은 짧은 실행(`claude -p … --mcp-config ~/.aquila/mcp/figma.json`)으로 `whoami`를 부르고, 결과를 `~/.aquila/figma-profile.json`에 캐시한다. Aquila Agents가 Figma 토큰을 직접 들 필요가 없다. 다만 `whoami` 응답 스키마는 공식 문서에서 확인되지 않았다. 2026-11-19 재확인 결과 공식 문서는 "identity, plans, and seats", 즉 이메일, 소속 플랜, 플랜별 시트 유형만 적고 필드명이나 플랜 티어 필드는 밝히지 않는다. 생성형 플러그인·셰이더에 필요한 `planKey`를 이 결과에서 얻는다는 언급만 있다 ([Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). 그러니 방어적으로 파싱하고, 티어를 읽지 못하면 "알 수 없음"으로 표시한다. 아래 표는 노트에서 확인한 공식 수치다. Figma가 수치를 자주 바꾸고 같은 페이지의 앞선 조회에서는 "월 6회"였으므로, **앱에 숫자를 하드코딩하지 말고 문서 링크로 연결해야 한다**.

Code Connect의 Professional 지원 여부는 Figma Help Center와 개발자 문서·스태프 답변이 서로 다르다. Professional에서는 토큰 scope가 없어 매핑이 거부된다는 사용자 보고도 있다 ([Forum 59258](https://forum.figma.com/ask-the-community-7/code-connect-on-the-professional-plan-docs-say-it-s-supported-but-there-s-no-code-connect-token-scope-and-mappings-are-rejected-59258)). 2026-10-27 Figma 커뮤니티 지원팀은 이 스레드에서 "On the Professional plan, creating Code Connect connections with MCP is not supported at this time"라고 답했다. Professional은 UI나 CLI로 만든 활성 연결(라이브러리 1개·프레임워크 1개)을 MCP가 읽을 수는 있지만 MCP로 만들 수는 없다는 뜻이다. 토큰 scope 문제는 그 스레드에서도 풀리지 않았다. 그러니 UI에는 "Organization 플랜이 필요할 수 있음"으로 표시해야 한다. Figma 설정은 **기본 꺼짐, 프로젝트별 토글**로 둔다. 백엔드 repo에서는 끄고, Figma 링크를 고정한 프로젝트에만 `--mcp-config`를 주입한다. 꺼진 상태에서는 Figma UI를 아예 숨기고, 켠 상태에서만 "Dev 시트 필요" 같은 비활성 사유를 툴팁으로 보여 준다(문구는 ko/en).

기대치 관리도 필요하다. Figma 스스로 "The MCP server is not a one-click 'design to perfect code' tool"이라고 말한다 ([toolradar](https://toolradar.com/blog/figma-mcp-server)). 사용자 불만도 충실도(여러 도구 비교에서 65~80%, 2차 인용), 토큰이 hex/px로 무너지는 문제, 느린 응답과 많은 토큰 소모에 몰려 있다 ([Figma Forum](https://forum.figma.com/report-a-problem-6/figma-mcp-can-t-get-good-results-have-tried-many-things-41861), [dev.to](https://dev.to/karthikeyan_sridhar_ecc11/my-ai-agent-guesses-design-tokens-repeatedly-mcp-doesnt-fix-it-either-570m)). 통하는 우회책은 `get_variable_defs`로 토큰을 먼저 받고, `get_design_context`를 섹션 단위로 부르고, Code Connect를 세팅하는 것이다 ([cc.bruniaux.com](https://cc.bruniaux.com/guide/workflows/design-to-code/)). **[추론]** Aquila Agents가 제공할 것은 그래서 프롬프트 칩이다. 터미널에 Figma 링크를 붙이면 "기존 컴포넌트와 토큰으로 이 프레임 구현"(토큰 먼저 받기 포함) 같은 템플릿 칩을 띄운다. 프론트엔드에는 `download_assets` 에셋 추출을, 백엔드에는 `get_figjam`(플로우)과 `get_comments`(미해결 코멘트를 TODO로)를 같은 방식으로 제공한다 ([Figma Tools and prompts](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/)). "구현 이후 디자인이 바뀌었나" 알림도 가능하다. Figma webhook은 수신 서버가 필요하므로 REST `/v1/files/:key` 버전 폴링이 현실적이다. 다만 REST에는 별도 토큰이 필요하고 Tier별 한도가 있으므로 고급 옵션으로 둔다.

**Claude in Chrome으로 Figma 캔버스를 검사하는 방식은 권장하지 않는다.** Figma 웹 캔버스는 WebGL로 렌더링되고, DOM으로 레이어나 Dev Mode 값을 읽는다는 근거는 공식에도 커뮤니티에도 없었다. 보이는 것은 캔버스 픽셀 수준일 가능성이 높다(**[추론]**, [Figma Forum: WebGL](https://forum.figma.com/report-a-problem-6/unable-to-access-a-particular-page-in-my-figma-file-due-to-webgl-error-popop-54778)). 커뮤니티의 표준 조합은 역할을 나눈다. Figma MCP가 디자인의 ground truth를, 브라우저 MCP(Chrome DevTools MCP, Playwright MCP)가 **구현된 localhost**의 렌더 ground truth를 맡고, 일치할 때까지 반복한다. Chrome DevTools MCP는 쿠키 없는 clean profile이라 로그인이 필요한 페이지에서는 Claude in Chrome(`--chrome`)을 쓴다 ([wmedia.es](https://wmedia.es/en/tips/claude-code-figma-chrome-mcp-pixel-perfect)). 이 루프를 앱 안에서 보이게 하는 것이 **앱 내 프리뷰**다. 2026년에는 Claude Code 데스크톱(⌘⇧B 브라우저, ⌘⇧S 요소 선택, `.claude/launch.json` dev server 관리), Cursor Design Mode(다중 선택, 마크업, 컴포넌트 스택 전송), Codex 앱(Annotation mode)이 모두 "임베디드 브라우저 + 요소를 골라 프롬프트에 첨부"를 갖췄다 ([Desktop docs](https://code.claude.com/docs/en/desktop), [Cursor Design Mode](https://cursor.com/docs/agent/design-mode), [Codex in-app browser](https://developers.openai.com/codex/app/browser)). 그런데 dev server용 point-and-prompt를 Claude Code CLI에 요청한 이슈 #91521은 2026-11-07에 **stale로 not planned 종료**됐다 ([#91521](https://github.com/anthropics/claude-code/issues/91521)). **[추론]** CLI 생태계에 이 기능이 비어 있다는 뜻이고, Aquila Agents가 claude와 codex 양쪽에 같은 UX를 줄 수 있는 자리다. 구현은 이렇게 한다. dev server는 `.claude/launch.json`과 pty 출력의 `localhost:\d+`로 감지한다. Electron `WebContentsView`에 디바이스 프리셋(390/768/1440)을 둔다. Select 모드에서 selector, 텍스트, computed style, 가능하면 React 컴포넌트명을 모으고 `capturePage(rect)`로 크롭한다. 이 결과를 활성 세션 입력창에 텍스트와 이미지 경로로 넣는다. 그 위에 Figma `get_screenshot`과 프리뷰 스크린샷을 겹쳐 보는 "Design vs Build" 뷰를 얹는다. 프리뷰를 CDP 포트로 노출해 `chrome-devtools-mcp --browserUrl`로 붙이면 사람과 에이전트가 같은 화면을 공유할 수 있다는 아이디어도 있지만 사례가 없어 **검증이 필요하다**. 디자이너가 터미널을 두려워한다는 증거("just looks like complicated terminal thing… no interface" — [ADPList](https://adplist.substack.com/p/claude-code-guide-for-designers))를 생각하면, 터미널 + 프리뷰 + Figma 패널 레이아웃의 "디자이너 프리셋"이 온보딩 장벽을 크게 낮출 것이다.

## 트렌드 버튼은 "내 CLI의 새 기능"부터 보여 줘야 쓸모가 있다

하네스 경쟁의 축은 모델보다 제어면(control plane)으로 옮겨 갔다. hooks, 권한 모드, 백그라운드 슈퍼바이저, 원격 제어가 그것이다. Claude Code hooks 이벤트는 30개를 넘었고 핸들러 타입은 `command`·`http`·`mcp_tool`·`prompt`·`agent`의 5종이다. Codex도 2026년에 hook을 정식화했다 ([Hooks docs](https://code.claude.com/docs/en/hooks), [Codex hooks](https://developers.openai.com/codex/hooks)). 서브에이전트 쪽에서는 Claude Code agent teams(v2.1.32, 2026-02-05, 여전히 실험적), agent view(v2.1.139, 2026-05-11), Codex 서브에이전트 GA(2026-03-16)가 나왔다 ([CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md), [Simon Willison](https://simonwillison.net/2026/Mar/16/codex-subagents/)). ADE 쪽에서는 Cursor 3 Agents Window(2026-04-02), Claude Code 데스크톱 재설계(2026-04-14), Warp ADE 오픈소스(2026-04-28), Antigravity 2.0(2026-05-19)이 모두 "세션 사이드바 + 상태 필터 + 워크트리 + diff 리뷰"로 수렴했다 ([Cursor 3.0](https://cursor.com/changelog/3-0), [MacRumors](https://www.macrumors.com/2026/04/15/anthropic-rebuilds-claude-code-desktop-app/), [Warp newsroom](https://www.warp.dev/newsroom/2026/4/28/warp-open-sources-its-agentic-development-environment), [Antigravity blog](https://antigravity.google/blog/introducing-google-antigravity-2/)). 눈여겨볼 신호도 있다. Claude Code 2.1.328(2026-11-19)은 "apps that embed Claude Code"용 옵션을 추가했다 ([CHANGELOG](https://raw.githubusercontent.com/anthropics/claude-code/main/CHANGELOG.md)). Aquila Agents 같은 임베드 호스트가 공식적으로 고려되는 사용 형태가 됐다는 뜻이다.

변화가 이렇게 빠르다는 사실 자체가 버튼의 근거다. Claude Code는 최근 30개 릴리스가 2026-10-07~11-19 사이에 나왔다. **거의 매일 릴리스**하는 셈이다 ([GitHub Releases API](https://api.github.com/repos/anthropics/claude-code/releases)). 노트에서 2026-11-19에 직접 확인한 무인증 소스는 다음과 같다. GitHub Releases API/Atom(claude-code, codex), Claude Code CHANGELOG.md(약 1.3MB), OpenAI News RSS, Cursor changelog RSS, Antigravity blog RSS, Simon Willison Atom, Latent Space RSS, HN Algolia API(`points%3E100`처럼 `>`를 반드시 인코딩해야 함). 반면 **Anthropic 뉴스 RSS는 404로 없고**, Warp 블로그 RSS도 404이며, Codex changelog의 "rss.xml"은 HTML을 돌려준다. GitHub 무인증 한도는 **IP당 60 req/h**이므로 ETag 조건부 요청이 필수다. Codex 릴리스에는 같은 날 alpha가 여럿 섞이므로 prerelease를 걸러야 한다 ([Codex releases](https://api.github.com/repos/openai/codex/releases), [HN Algolia](https://hn.algolia.com/api/v1/search_by_date?query=claude%20code&tags=story&numericFilters=points%3E100), [OpenAI RSS](https://openai.com/news/rss.xml), [Cursor RSS](https://cursor.com/changelog/rss.xml)).

**[추론/권장]** 설계는 이렇게 한다. main 프로세스가 앱 시작 시와 6시간마다 가져와 `~/.aquila/news-cache.json`에 캐시하고, 새 IPC 채널(`IPC.newsList`)로 렌더러에 넘긴다(규칙 2). 패널은 두 탭이다. 첫 탭 "내 CLI 업데이트"는 사용자의 `claude --version`/`codex --version`보다 새 릴리스의 "Added" 줄만 3~5개 하이라이트로 보여 준다. 사용자에게 가장 실용적인 정보다. 둘째 탭 "업계 흐름"은 1st-party RSS와 HN을 키워드(subagent, hook, agent view, ADE, harness)로 분류해 보여 준다. 사이드바 상단 띠에 버튼 하나와 미확인 개수 배지를 둔다. 원문 전재는 피하고 제목·링크·짧은 발췌만 보여 준다(법률 검토 아님). LLM 요약은 이미 임베드한 `claude -p`를 쓰는 **옵트인** 방식으로 둔다. 사용자 쿼터를 쓰기 때문이다. 처음에는 키워드 규칙 분류로 충분하다. 인앱 "What's new"를 잘 구현한 앱 사례는 노트에서 확보하지 못했으므로 이 UI는 추론이다.

## 배터리와 부드러움은 WebGL 4개, xterm 6, 출력 배치로 대부분 결정된다

현재 코드에는 확인된 위험이 하나 있다. `TerminalView.tsx`는 **세션마다 `WebglAddon`을 로드**하고, 숨긴 세션도 mount 상태로 둔다. 데스크톱 Chromium은 활성 WebGL 컨텍스트가 약 16개를 넘으면 "Too many active WebGL contexts. Oldest context will be lost"를 띄우며 가장 오래된 컨텍스트를 버린다 ([WebKit commit](https://webkit.googlesource.com/WebKit/+/70e10861eb2fbd9d0862fd8702874c25ae5d8bfd%5E%21), [Plotly 커뮤니티](https://community.plotly.com/t/too-many-active-webgl-contexts/16379)). 지금은 `onContextLoss`에서 dispose만 하므로, 세션이 15개를 넘는 순간 오래된 탭이 조용히 DOM 렌더러로 떨어지거나 오래된 프레임을 보여 줄 수 있다. kolu는 포커스된 타일만 WebGL을 쓰고, dispose 직후 `term.refresh(0, rows-1)`로 강제 repaint해 이 문제를 풀었다 ([kolu #1299](https://github.gg22.workers.dev/juspay/kolu/issues/1299)). Paradev는 숨긴 터미널의 GPU 컨텍스트와 스크롤백을 정리해 16개 터미널 기준 **GPU 컨텍스트를 16→4개, 렌더러 RSS를 1,127MB→838MB**로 줄였다고 밝혔다 ([Paradev changelog](https://superset.sh/changelog/2026-07-19-performance-memory-and-load), 자사 측정). xterm.js는 IntersectionObserver로 보이지 않는 터미널의 렌더링을 이미 멈추므로 ([xterm.js#880](https://github.com/xtermjs/xterm.js/issues/880)), **보이는 pane(최대 4개)에만 WebGL을 붙이는 것**이 안정성, GPU 메모리, 전력을 함께 해결한다. 숨긴 세션에 남는 비용은 렌더링이 아니라 파싱이다(**[추론]**).

두 번째 지렛대는 xterm.js 버전이다. 현재 `package.json`은 `@xterm/xterm ^5.5.0`인데, **DEC 2026 synchronized output은 6.0.0에서 추가됐다**(#5453). Claude Code는 시작할 때 터미널의 synchronized output 지원 여부를 probe해서 지원하면 사용한다 ([xterm 6.0.0](https://newreleases.io/project/npm/@xterm/xterm/release/6.0.0), [Claude Code: Fullscreen](https://code.claude.com/docs/en/fullscreen)). 6.0에는 메모리 누수 수정과 smooth scroll 프레임당 1회 제한도 들어 있다. 반대로 스크롤바와 viewport 동작이 "매우 다르게" 바뀌는 breaking change가 있으므로 smoke와 스크롤 코드를 다시 확인해야 한다. 2026-11-19에 [6.0.0 릴리스 노트](https://github.com/xtermjs/xterm.js/releases/tag/6.0.0)를 다시 확인했다. canvas 렌더러 addon 제거(#5105), `overviewRulerWidth` → `overviewRuler`(#5107), Alt→Ctrl+화살표 변환 제거(#5346), `windowsMode`·`fastScrollModifier` 옵션 제거(#5462)도 있다. IME 쪽으로는 일부 IME 중복 입력 수정(#5024)이 들어 있다. 짝이 되는 addon은 같은 날(2025-12-22) 나온 `addon-webgl` 0.19.0, `addon-fit` 0.11.0, `addon-web-links` 0.12.0이다. 그런데 현재 `package.json`은 xterm 5.5.0에 6.0용 `addon-webgl` 0.19.0을 섞어 쓰고 있다. 5.5와 짝인 버전은 0.18.0이다. Wave Terminal은 2026-03에 6.0으로 올렸다 ([waveterm #3095](https://gh.r-mj.com/wavetermdev/waveterm/pull/3095)). Claude Code 자체도 2026년에 **fullscreen(alt-screen) 렌더러**를 만들었다. 보이는 메시지만 그리고 바뀐 셀만 보내서 "깜빡임을 없애고 긴 대화에서도 메모리를 평평하게 유지"한다. 효과는 xterm.js 같은 처리량 병목 터미널에서 가장 크다 ([Fullscreen docs](https://code.claude.com/docs/en/fullscreen)). classic 렌더러는 세션이 길어질수록 화면 diff CPU 비중이 0.2%에서 48%까지 오른다는 커뮤니티 프로파일링도 있다 ([DEV: profiled Claude Code](https://dev.to/vmitro/i-profiled-claude-code-some-more-part-2-do-androids-dream-of-on-diffs-2kp6)). **[추론]** 규칙 6에 따라 env를 강제하지는 말고, 설정에 "Aquila Agents가 띄우는 Claude 세션을 fullscreen으로"(spawn할 때만 `CLAUDE_CODE_NO_FLICKER=1` 주입) 토글을 두는 것이 적절하다. fullscreen 세션은 대화가 xterm 스크롤백에 남지 않으므로, 세션 종류별로 스크롤백을 차등화하면 메모리를 아낄 수 있다(현재는 일괄 10,000줄). macOS fullscreen 렌더러에서 줄 중복 버그 보고가 있으므로 ([#67215](https://claudeissues.com/issue/67215-bug-fullscreen-no-flicker-alt-screen-renderer-duplicates-content-lines-on-wrappe)) 기본값으로 켜지는 않는다.

세 번째는 데이터 경로와 폴링이다. xterm.js 공식 흐름 제어 가이드에 따르면 처리 속도는 약 5–35MB/s이고, 내부 write 버퍼가 50MB를 넘으면 **데이터를 버린다**. 권장안은 약 100KB마다 write callback을 붙이고 대기 수 HIGH=5면 pause, LOW=2면 resume하는 방식이며, IPC를 거치면 렌더러가 ACK를 보내야 한다. 검증은 `yes`를 실행하고 Ctrl-C 반응 시간을 보면 된다 ([xterm.js Flow Control](https://xtermjs.org/docs/guides/flowcontrol/)). **[추론]** node-pty 출력을 main에서 16ms 또는 64–100KB 단위로 묶어 보내고, 숨긴 세션은 100–250ms로 늘린다. 상태 판정은 pty 데이터를 직접 받는 main으로 옮기고 렌더러는 상태 "전환" 이벤트만 받게 하면, React 리렌더 폭주와 `backgroundThrottling`에 따른 판정 지연이 함께 사라진다. 5초마다 도는 git 폴링(`git status` + `git diff` 두 번 spawn)은 `fs.watch` 재귀 감시(macOS는 FSEvents 기반)와 300–500ms debounce, lazy diff로 바꾸고, 30–60초 폴링은 안전망으로만 남긴다. 분당 약 500개 git 프로세스를 spawn한 Cursor가 반면교사다 ([Cursor forum](https://forum.cursor.com/t/multi-root-workspace-agent-branch-tracker-and-per-file-git-root-lookups-spawn-500-git-processes-minute/171642)). Electron `powerMonitor`는 `on-battery`, `thermal-state-change`, `speed-limit-change` 이벤트를 제공하지만 **Low Power Mode API는 없다** ([Electron powerMonitor](https://electronjs.org/docs/latest/api/power-monitor)). 플랫폼 차이도 있다. `on-battery`/`on-ac`와 `speed-limit-change`는 macOS와 Windows 모두에서 오지만, `thermal-state-change`는 macOS 전용이다. 이 이벤트들로 "절전 프로필"을 트리거해 폴링 간격을 늘리고, 커서 깜빡임과 무한 애니메이션을 끈다. 리사이즈도 손볼 곳이 있다. 현재 ResizeObserver가 매번 `fit()`을 호출해 pty resize와 Ink 전체 재그리기를 유발할 수 있으므로, rAF로 합치고 cols·rows가 실제로 바뀔 때만 호출한다.

마지막으로 T9의 "numbers, not guesses"에는 근거가 있다. 공개된 엄밀한 터미널 배터리 벤치마크는 없다. 근거는 Activity Monitor 일화가 전부다. 한 사용자의 12시간 Energy Impact에서 Ghostty는 3,600, Claude 데스크톱은 46이었다(상대값, 1인 측정 — [DEV](https://dev.to/frr149/your-terminal-is-burning-battery-like-its-mining-bitcoin-4e7l)). 리소스 문제의 주범이 래퍼가 아니라 Claude Code 프로세스일 때도 많다. 유휴 인스턴스당 CPU 10~100%, 24시간 뒤 30GB 이상 메모리, 그리고 `claude --resume`으로 재시작하면 정상화된다는 보고들이 있다 ([#30807](https://github.com/anthropics/claude-code/issues/30807), [#9711](https://github.com/anthropics/claude-code/issues/9711), [#22968](https://github.com/anthropics/claude-code/issues/22968)). **[추론]** T12 시스템 모니터는 세션별 pty 프로세스 트리의 CPU·RAM을 보여 주고, "유휴인데 CPU 높음" 세션을 강조하고, **원클릭 resume 재시작**을 제공해야 한다. 측정 루프는 `powermetrics --samplers tasks`의 idle wakeups/s, Energy 탭의 12시간 전력, `yes` Ctrl-C 테스트로 구성하고, Ghostty·iTerm2와 같은 시나리오(Claude 5개, 1개 스트리밍)에서 비교한다. 이 도구들(`powermetrics`, Activity Monitor)과 T12가 상정한 `vm_stat`·`sysctl`·`pmset`·`memory_pressure`·`ps`는 모두 macOS 전용이다. Windows 대응은 아래 Windows 절에 정리했다. 수치를 공개하면 "Electron이라 무겁다"는 의심에 대응할 수 있다.

## Windows는 경쟁자가 비워 둔 시장이지만, 플랫폼 계층부터 깔아야 열린다

### 두 CLI는 네이티브 Windows를 지원하고, 경쟁 앱 셋은 Windows가 없다

Windows 지원은 오너의 새 요구 사항이고, 기회도 분명하다. 두 CLI 모두 **네이티브 Windows를 공식 지원**하고, WSL은 선택지다. Claude Code는 Windows 10 1809+와 x64·ARM64를 지원한다. Git for Windows가 있으면 Git Bash를, 없으면 PowerShell을 도구 셸로 쓴다. 다만 **샌드박스는 WSL2에서만** 지원된다 ([Claude Code setup](https://code.claude.com/docs/en/setup)). Codex는 "PowerShell에서 네이티브로" 돌고 자체 Windows 샌드박스를 갖췄다. 권장 구현인 `mxc`는 Windows 11 24H2(build 26100.9278) 이상을 요구하고, Windows 10은 best effort다 ([Codex Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox)). 경쟁 지형을 보면 **Conductor는 macOS 전용(Windows 대기자 명단), Superset은 Windows 미지원**이고, cmux는 네이티브 macOS 앱이다 ([cloudroom.dev](https://www.cloudroom.dev/blog/conductor-alternatives), [superset.sh 비교](https://superset.sh/compare/conductor-alternative), [agentastic.dev](https://www.agentastic.dev/alternatives/cmux)). Pane이 Win11 + Ubuntu 24.04 WSL2에서 30개 앱을 테스트한 결과(벤더 글), 네이티브 Windows 빌드가 있는 앱은 14개였고 **WSL 레포에서 에이전트를 제대로 돌린 앱은 6개**뿐이었다. 같은 테스트에서 Maestri는 첫 실행에 에이전트 설정으로 스킬 28개를 설치했고, Reliant는 PATH를 수정해 `~/.claude`·`~/.codex` 백업을 권고했다 ([runpane.com](https://runpane.com/agent-managers-for-windows)). 그러니 Aquila Agents의 규칙 6(사용자 CLI 설정 무수정)은 Windows에서 그대로 마케팅 포인트가 된다. 반대로 OpenAI의 Codex 데스크톱조차 WSL 브리징에서 버그를 냈다. WSL을 골랐는데 PowerShell 5.1에서 스레드가 시작되고 `C:\mnt\c` 같은 잘못된 경로가 나왔다. WSL에 CLI가 없으면 재연결 루프를 돌며 약 20초마다 `wsl.exe`를 폴링했다 ([codex#28302](https://github.com/openai/codex/issues/28302), [#62097](https://github.com/openai/codex/issues/62097)). "Windows + WSL을 제대로"가 차별점이 되는 이유다.

### 플랫폼 계층과 http hook이 다른 모든 Windows 작업의 전제다

지금의 실행 패턴 `$SHELL -l -i -c "<cmd>; exec $SHELL -l -i"`는 Windows로 옮겨지지 않는다. 사실상 표준은 VS Code와 Windows Terminal의 방식이다. 셸을 자동 감지하고(PowerShell 7 > Windows PowerShell, Git Bash, CMD, WSL 배포판별), "기본 프로필"을 고르게 하고, 프로필별로 args/env를 둔다. WSL 프로필은 `wsl.exe -d <distro>`로 실행한다 ([VS Code terminal profiles](https://code.visualstudio.com/docs/terminal/profiles), [WSL basic commands](https://learn.microsoft.com/en-us/windows/wsl/basic-commands)). **[추론]** 셸 탐지, spawn 템플릿, 경로 변환, 단축키, 알림을 `electron/platform/{darwin,win32}.ts`로 모은다. 템플릿 제안은 다음과 같다.

| 셸               | spawn 템플릿(제안)                                                     | 비고                                                                                                                                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PowerShell 7/5.1 | `pwsh.exe -NoLogo -NoExit -Command "claude"`                           | `-NoExit`가 `exec $SHELL` 역할. MS Store `WindowsApps` 앨리어스 경로는 피하고 `C:\Program Files\PowerShell\7\pwsh.exe` 우선 ([codex#18937](https://github.com/openai/codex/issues/18937))                                                |
| CMD              | `cmd.exe /K claude`                                                    |                                                                                                                                                                                                                                          |
| Git Bash         | `bash.exe -l -i -c "claude; exec bash -l -i"`                          | 현재 macOS 로직 재사용                                                                                                                                                                                                                   |
| WSL              | `wsl.exe -d <distro> --cd <path> -- bash -lic "claude; exec bash -li"` | `--cd`: `~`=Linux 홈, `/`로 시작=Linux 절대경로, 그 외=Windows 절대경로 (2026-11-19 [WSL `--help` 원문](https://github.com/microsoft/WSL/blob/master/localization/strings/en-US/Resources.resw)으로 확인. MS Learn 명령 페이지에는 없음) |

경로는 `C:\…` ↔ `/mnt/c/…`가 단순 규칙이지만 사용자가 automount 루트를 바꿨을 수 있다. **[추론·검증 필요]** `wsl.exe -e wslpath -a`로 변환하고 `\\wsl.localhost\<distro>\…` 경로를 인식한다. `wsl --list` 출력은 UTF-16LE라서 디코딩에 주의해야 한다. 프로젝트마다 "실행 환경(네이티브 / WSL 배포판)"을 저장한다. Pane이 이를 강점으로 내세우고, `\\wsl$` 경로를 Windows git으로 여는 방식은 느리고 리눅스 전용 스크립트가 깨진다고 지적한다 ([runpane.com](https://runpane.com/agent-managers-for-windows)). Codex의 폴링 사고를 반면교사로 삼아, WSL 탐지는 앱 시작 시 1회와 사용자 요청 시에만 한다. git 패널도 같은 계층을 탄다. `git.exe` 경로를 탐지하고, WSL 프로젝트는 `wsl.exe -e git`으로 돌린다.

hook은 **모든 플랫폼에서 `type: "http"`로 전환**하는 것이 1순위다. Windows의 shell-form command hook은 Git Bash, 없으면 PowerShell로 실행된다. Git Bash가 없으면 `PreToolUse`/`PermissionRequest`에서 0·2 외의 exit code를 실패로 보고 **tool call을 막는다**. PowerShell에서는 따옴표 문자열만 있는 command가 실행되지 않고 출력된다 ([Claude Code hooks](https://code.claude.com/docs/en/hooks)). `http` hook은 셸 없이 Claude가 이벤트 JSON을 직접 POST한다. 필드는 `url`, `headers`(`allowedEnvVars`로 `$VAR` 보간), `onFailure`(`continue`/`block`, v2.1.295+), `timeout`(기본 600초)이다. 연결이 실패해도 비차단 오류로 끝난다 (같은 문서). **[추론]** `{"type":"http","url":"http://127.0.0.1:<port>/hook/<event>","headers":{"X-Aquila Agents-Session":"$AQUILA_TAB_ID"},"allowedEnvVars":["AQUILA_TAB_ID"],"timeout":5,"onFailure":"continue"}`로 바꾸면 따옴표와 셸 문제가 사라지고, macOS에서도 이벤트마다 `curl` 프로세스를 띄우던 비용이 없어진다. 앞 절의 `PermissionRequest`·`StopFailure` 추가와 같은 파일을 고치므로 함께 하는 것이 맞다. 구버전 Claude Code를 위한 command+curl 폴백 여부는 `claude --version`으로 결정한다. WSL 세션에는 함정이 있다. hook은 WSL 안에서 실행되므로, `127.0.0.1`이 Windows 호스트를 가리키는지는 WSL 네트워킹 모드(mirrored/NAT)에 달려 있다. 2026-11-19 [MS Learn: WSL networking](https://learn.microsoft.com/en-us/windows/wsl/networking)으로 확인했다. 기본값인 NAT에서는 WSL→Windows 연결에 호스트 IP(`ip route show | grep -i default | awk '{print $3}'`)가 필요하고, 이 연결은 LAN 연결로 취급되므로 `127.0.0.1` 바인딩으로는 받을 수 없다. mirrored 모드(Windows 11 22H2+, `.wslconfig`의 `networkingMode=mirrored`)에서는 `127.0.0.1`로 Windows 서버에 닿는다(`::1`은 불가). WSL 2.0.9+에서는 Hyper-V 방화벽이 기본으로 켜진다. 그러니 NAT 모드라면 호스트 IP를 env로 주입하고, 서버를 토큰 인증과 함께 바인딩해야 하며, Windows 방화벽도 확인해야 한다. 상태 판정을 OSC 7501로 옮기면 이 문제 자체가 상태 경로에서 빠진다(아래 권고).

### ConPTY는 동시 spawn/kill에 약하므로 kill 경로를 직렬화해야 한다

node-pty는 이제 **ConPTY만** 쓰고 Windows 10 1809+가 필수다. 빌드에는 Python, C++ 컴파일러, Windows SDK, Spectre-mitigated libs가 필요하다 ([node-pty README](https://github.com/microsoft/node-pty), [node-pty#842](https://github.com/microsoft/node-pty/issues/842)). 문제는 Aquila Agents가 정확히 "여러 세션을 동시에 spawn/kill하는" 형태라는 점이다. 이 상황에서 `conpty_console_list_agent`가 "AttachConsole failed"로 크래시하고 exit 이벤트가 오지 않는다는 보고가 있다(node-pty 1.1.0~1.2.0-beta, Win11) ([node-pty#1007](https://github.com/microsoft/node-pty/issues/1007)). 자연 종료 뒤 conhost.exe가 고아로 남거나 ([qwen-code#11497](https://github.com/QwenLM/qwen-code/pull/11497)), 이미 끝난 셸을 kill할 때 0xC0000005로 크래시한다는 보고도 있다 ([clawdling#4](https://github.com/jddavenportOpen/clawdling/issues/4)). **[추론]** kill을 짧은 큐로 직렬화하고, 이미 exit한 pty는 kill하지 않으며, 앱 종료 시 남은 conhost를 정리한다. node-pty는 Windows 러너에서 x64·arm64별로 Electron 45 ABI에 맞춰 리빌드한다. 렌더러에는 `windowsPty: { backend: 'conpty', buildNumber }`를 반드시 설정한다. 그래야 ConPTY가 아래에 빈 줄을 추가하는 동작에 맞춰 reflow와 스크롤백이 정상으로 처리된다 ([xterm 5.3 typings](https://cdn.jsdelivr.net/npm/xterm@5.3.0/typings/xterm.d.ts)). buildNumber는 main이 IPC로 넘긴다.

### 단축키는 Ctrl+Shift 계열로, 타이틀바는 titleBarOverlay로 바꾼다

⌘를 Ctrl로 단순 치환하면 Ctrl+C/V/W/T가 터미널과 정면으로 충돌한다. Windows Terminal 기본값은 Ctrl+Shift+W(닫기), Ctrl+Shift+P(명령 팔레트), Alt+Shift+D(분할), Alt+화살표(포커스 이동), Alt+Shift+화살표(리사이즈)다 ([Windows Terminal panes](https://learn.microsoft.com/en-us/windows/terminal/panes)). **[추론]** 매핑은 이렇게 제안한다. ⌘T/⌘W/⌘K/⌘⇧G는 Ctrl+Shift+T/W/K/G로, ⌘1–9는 Ctrl+1–9 또는 Alt+1–9로, ⌘⌥화살표는 Windows Terminal과 같은 Alt+화살표로 옮긴다. Ctrl+C는 선택 영역이 있으면 복사, 없으면 SIGINT로 보낸다. Ctrl+V는 pty로 그대로 넘긴다. Claude Code가 이미지 붙여넣기에 쓰기 때문인데, Windows에서 Ctrl+V 이미지 붙여넣기가 무반응이라는 보고와 Windows는 Alt+V라는 2차 출처가 함께 있으니 실측이 필요하다 ([#57316](https://github.com/anthropics/claude-code/issues/57316), [felloai](https://felloai.com/claude-code-images/)). ⌘⌥T 같은 Ctrl+Alt 조합은 유럽 키보드의 AltGr과 겹쳐 문자 입력을 깨므로 피한다 **[추론·검증 필요]**. 단축키 정의는 shared 계층의 플랫폼 독립 맵(`CommandOrControl` 류) 하나로 두고, ⌘K 팔레트, ⌘/ 가이드, 메뉴가 모두 그 맵을 읽게 한다. 타이틀바는 Windows에서 `titleBarStyle: 'hidden'` + `titleBarOverlay`가 필수다. `height`를 `--size-titlebar`와 맞추고 `color`/`symbolColor`를 토큰에서 가져오며, CSS `env(titlebar-area-x/width/height)`로 창 컨트롤 영역을 피한다 ([Electron custom title bar](https://www.electronjs.org/docs/latest/tutorial/custom-title-bar)). 창 컨트롤이 왼쪽 신호등이 아니라 오른쪽에 오므로, 탭 바 오른쪽 끝의 레이아웃을 다시 봐야 한다. Windows 11 snap layouts와의 상호작용은 노트에서 확인하지 못했다.

### 계정은 env로, 알림은 AppUserModelID로, WSL 세션은 별도 로그인으로 다룬다

계정 분리는 Windows에서 오히려 단순하다. Keychain이 없고, `CLAUDE_CONFIG_DIR`을 주면 `.credentials.json`이 그 디렉터리에 저장된다 ([authentication](https://code.claude.com/docs/en/authentication)). Aquila Agents가 spawn하는 세션은 node-pty `env`에 `CLAUDE_CONFIG_DIR`을 넣으면 셸 종류와 무관하게 동작한다. 그러니 T2의 zsh 함수에 해당하는 PowerShell `$PROFILE` 함수 쓰기는 후순위로 둔다. 하더라도 사용자 확인이 필수다(PowerShell 7과 5.1의 프로필 경로가 다르고 OneDrive 리디렉션이 흔하다 **[추론·검증 필요]**). shared 계정에서 변수를 비워 두는 규칙은 Windows에서도 유지한다. WSL 세션은 WSL 내부 `~/.claude`를 쓰므로 Windows 쪽 로그인과 따로다. Pane이 "WSL에서 기존 로그인 재사용"을 기능으로 내세울 만큼 실제 마찰이다 ([runpane.com](https://runpane.com/agent-managers-for-windows)). 그러니 계정 UI에는 "이 WSL 배포판에서는 따로 로그인해야 함"을 표시한다. Windows 알림이 뜨려면 Start Menu 바로가기에 AppUserModelID와 ToastActivatorCLSID가 있어야 한다. 개발 중에는 `app.setAppUserModelId()`를 직접 호출해야 하고, 알림 액션 버튼은 `action` 이벤트로, 집중 모드 여부는 `windows-notification-state` 모듈로 확인한다 ([Electron notifications](https://www.electronjs.org/docs/latest/tutorial/notifications)). 휴지통 이동(T11)은 `shell.trashItem`이 Windows 휴지통으로 동작할 가능성이 높다. 문구만 "휴지통/Recycle Bin"으로 맞춘다 **[추론]**.

### 서명은 한국 개인 개발자에게 가장 큰 벽이다

electron-builder는 `win.sign`에 Azure 백엔드를 지원한다 ([electron-builder](https://www.electron.build/docs/features/code-signing/code-signing-win)). Electron 문서는 Azure Artifact Signing이 SmartScreen 경고를 없앤다고 적는다. 반면 Microsoft는 **즉시 신뢰를 주지 않고 평판은 다운로드 이력으로 쌓인다**고 하고, 자격도 **개인은 미국·캐나다만**이다. 조직은 2026-11-19 확인 기준 미국·캐나다·EU·UK·호주·뉴질랜드·일본·**한국**·싱가포르·스위스·노르웨이·이스라엘이다([Artifact Signing quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart), 2026-11-17 갱신. 기존 노트의 "조직은 미국·캐나다·EU·UK"는 낡은 정보였다) ([Electron code signing](https://electronjs.org/docs/latest/tutorial/code-signing), [Microsoft code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options)). 2026-03-26 intermediate CA 교체 뒤 서명된 릴리스에서 경고가 다시 떴다는 커뮤니티 보고도 있다 ([Microsoft Q&A 미러](https://dotnet.territoriali.olinfo.it/en-us/answers/questions/5855442/azure-trusted-signing-new-intermediate-cas-causing)). 한국 개인 개발자는 Azure 자격이 없다. 다만 **한국 법인은 Public Trust 대상**이므로, 법인을 세우면 OV/EV 인증서보다 Artifact Signing이 더 싼 선택지가 된다(유료 Azure 구독 필수, EV는 발급하지 않음 — [Artifact Signing FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq)). 선택지는 세 가지다. (a) 법인을 세운 뒤 OV/EV 인증서(클라우드 HSM), (b) 초기에는 미서명 배포 + winget/scoop + README의 SmartScreen 안내, (c) MS Store(MSIX). MSIX는 파일시스템 가상화 때문에 `~/.aquila`, node-pty 자식 프로세스, `%USERPROFILE%\.claude` 접근에 제약이 생길 수 있다 **[추론·검증 필요]**. 그래서 터미널 앱에는 NSIS + electron-updater가 무난하다. 사용자는 Snapdragon용 ARM64 빌드도 기대한다 ([runpane.com](https://runpane.com/agent-managers-for-windows)). 서명 경로는 T8을 진행하기 전에 결정해야 하는 비기술적 선행 과제다.

### 한글 IME와 시스템 모니터는 Windows에서 따로 검증해야 한다

Windows의 한글 문제는 macOS와 양상이 다르다. Claude Code no-flicker(fullscreen) 렌더러에서는 한글 붙여넣기가 UTF-8→Windows-1252로 깨지고, 우회책은 `CLAUDE_CODE_NO_FLICKER=0`이다 ([#65806](https://github.com/anthropics/claude-code/issues/65806)). 앞 절에서 제안한 "fullscreen 토글"을 Windows에서는 기본으로 꺼 두고 경고를 붙여야 한다는 뜻이다. Win11 25H2의 IME 조합창 튐은 2.1.121에서 기본 Windows Terminal로 정상 동작한다는 보고 뒤 닫혔다 ([#51768](https://github.com/anthropics/claude-code/issues/51768)). Claude 데스크톱 실행 중 시스템 전역 한글 IME가 다른 앱에서 깨진다는 보고도 있어 ([#84395](https://github.com/anthropics/claude-code/issues/84395)), IME는 Windows에서 특히 민감하다. **[추론]** 앞 절의 IME 체크리스트를 Windows 러너에서도 돌린다. `--font-*` 토큰에는 `"Cascadia Mono", "D2Coding", Consolas` 폴백을 추가한다. D2Coding은 사용자 우회책으로 권장됐다. 일부 GPU, 원격 데스크톱, VM에서는 WebGL 컨텍스트 손실이 잦을 수 있으므로 DOM 폴백 경로가 더 중요해진다.

T12 시스템 모니터가 상정한 `vm_stat`/`sysctl`/`pmset`/`memory_pressure`/`ps`는 Windows에 없다. **[추론]** CPU는 `os.cpus()` times 델타로 플랫폼 공통 코드를 쓰고, `app.getAppMetrics()`로 앱 자체 사용량을 얻는다. `os.loadavg()`는 Windows에서 0을 돌려주므로 쓰지 않는다 **[검증 필요]**. 배터리와 메모리는 `Get-CimInstance Win32_Battery`와 `Win32_PerfFormattedData_PerfProc_Process`를 쓰되, PowerShell 기동이 수백 ms라 매번 spawn하지 말고 장수명 pwsh 하나를 유지한다. `wmic`은 Windows 11에서 deprecated이므로 쓰지 않는다. `systeminformation` 패키지는 Windows를 "partial"로 표기한다 ([systeminformation.io](https://systeminformation.io/)). "memory pressure"는 Windows에 직접 대응이 없으므로 가용/커밋 메모리 비율로 바꾸고 UI 문구를 플랫폼별로 둔다. T9의 배터리 측정도 `powermetrics` 대신 Windows 도구로 따로 설계해야 하는데, 노트에는 근거가 없어 미정으로 남긴다.

## 앱 내 가이드(? 버튼)로 "단축키 시트"를 기능 투어로 키운다

> 이 절은 웹 조사가 아니라 **오너의 요구 사항과 그에 대한 설계 제안**이다. 근거로 인용한 부분만 노트의 출처를 단다.

오너는 사이드바 하단의 `?` 아이콘(⌘/, Windows는 Ctrl+/)으로 여는 가이드 모달을 요구했다. 노트에는 이 방향을 받치는 근거가 있다. Claude Code 데스크톱은 **⌘/로 단축키 전체 목록**을 띄운다 ([Anthropic: desktop redesign](https://claude.com/resources/articles/claude-code-desktop-redesign)). zellij는 가능한 키를 상태바에 늘 보여 줘 "암기 부담을 없앴다"는 평을 받는다 ([Zellij 리뷰](https://jpk-io.pages.dev/dev-tools/zellij-terminal-multiplexer-review/)). 디자이너들은 터미널 도구를 "no interface, nothing visually intuitive"로 받아들인다 ([ADPList](https://adplist.substack.com/p/claude-code-guide-for-designers)). 강제 온보딩은 반발을 산다 ([itsfoss: Warp](https://itsfoss.com/news/warp-terminal-no-login/)). 앞 절에서 제안한 "⌘/ 단축키 시트"는 이 가이드에 흡수한다. 가이드 안에 "단축키" 항목을 두어 플랫폼별 표기로 전체 목록을 보여 주면, 진입점이 하나로 줄어든다.

**[설계 제안]** 모달 왼쪽은 기능 목록이다. 상태 점과 알림, 다음 대기 세션, 분할, Changes 패널, 계정 등이 들어가고, 검색 가능하게 한다. 오른쪽은 스크린샷이나 짧은 루프 애니메이션(앱에 번들된 WebP/MP4), 1~2줄 설명, 그 기능의 단축키다. `prefers-reduced-motion`이면 첫 프레임 정지 이미지를 보여 준다(규칙 4b와 같은 취지). 문구는 `dictionary.ts`의 ko/en을 쓴다. 단축키 표기는 앞의 플랫폼 독립 단축키 맵에서 읽어, macOS는 ⌘, Windows는 Ctrl+Shift로 자동 표기한다. 가이드 항목은 `{id, titleKey, bodyKey, media, shortcutId}` 레지스트리 하나로 관리한다. FSD 상으로는 모달 껍데기를 design-system 컴포넌트로, 가이드 콘텐츠를 feature 슬라이스로 둔다. 첫 실행에는 "둘러보기 / 건너뛰기"를 **한 번만** 제안하고, 본 여부는 `~/.aquila/` 설정에 저장한다. 앞서 말한 첫 실행 체크리스트(CLI 감지, 폴더 추가)가 끝난 뒤에 제안해야 첫 화면이 과밀해지지 않는다. Windows에서 Ctrl+/는 터미널에 `\x1f`로 전달돼 일부 CLI가 쓸 수 있으므로, 충돌 여부를 **검증해야 한다**. (2026-11-19 확인: xterm.js 6.0.0의 [`Keyboard.ts`](https://github.com/xtermjs/xterm.js/blob/6.0.0/src/common/input/Keyboard.ts)는 Ctrl+/를 제어 문자로 바꾸지 않는다. `\x1f`는 Ctrl+_와 Ctrl+7에서만 나온다. Windows Terminal 기본 키 맵에도 Ctrl+/는 없다. Claude Code의 undo는 `Ctrl+_`/`Ctrl+Shift+-`다([keybindings](https://code.claude.com/docs/en/keybindings)). 그러니 xterm.js 기반인 Aquila Agents에서 Ctrl+/를 가로채도 CLI 기능을 빼앗지 않는다. 다만 독일어 배열처럼 `/`가 Shift+7인 배열에서는 누르기 어려우므로 F1을 보조 키로 둔다 **[추론]**.)

화면이 낡지 않게 하는 장치가 핵심이다. 현재 `npm run smoke`는 앱을 띄워 pty 왕복을 확인하고 `webContents.capturePage()`로 `dist/smoke.png`를 저장한다(`electron/smoke.ts`). **[설계 제안]** 이를 시나리오 스크립트로 확장한다. 가이드 항목마다 데모 상태(예: 분할 2개 + waiting 세션 1개)를 연출하고 `capturePage(rect)`로 해당 영역을 ko/en 각각, 가능하면 다크/라이트와 macOS/Windows 러너별로 찍는다. 애니메이션은 프레임 시퀀스를 ffmpeg 등으로 WebP/MP4로 묶는다(도구 선택은 **검증 필요**). 레지스트리 항목에 미디어가 없으면 smoke가 실패하게 해 누락을 막고, PR diff에서 바뀐 스크린샷이 보이게 한다. 번들 크기가 늘어나므로 해상도와 길이(예: 3~5초)에 예산을 둔다. 데모용 가짜 세션 상태는 실제 사용자 데이터나 계정 정보가 찍히지 않게 고정 픽스처로만 연출한다.

## 릴리즈 노트 모달은 Aquila Agents 자신의 변화를, 트렌드 버튼은 바깥 소식을 보여 준다

> 이 절도 **오너의 요구 사항과 설계 제안**이다. 노트에는 인앱 "What's new" 구현 사례의 출처가 없었다.

**[설계 제안]** 업데이트 뒤 첫 실행에서 **한 번만** 뜬다. `~/.aquila/` 설정의 `lastSeenVersion`과 `app.getVersion()`을 비교해 현재 버전이 더 높을 때만 연다. **새로 설치한 경우에는 띄우지 않고** `lastSeenVersion`을 현재 버전으로 기록한다. 그 자리에는 가이드 둘러보기 제안이 뜬다. 레이아웃은 가이드와 같은 모달 컴포넌트를 쓴다. 왼쪽에 이번 버전의 헤드라인 변화 3~5개, 오른쪽에 스크린샷이나 애니메이션과 설명을 둔다. 각 항목에는 "사용법 보기" 링크를 달아 가이드의 해당 기능 페이지(`guideId`)로 바로 이동시킨다. 다시 볼 때는 `?` 메뉴의 "새로운 기능"으로 열고, 지난 버전 목록에서 과거 노트도 고를 수 있게 한다. 여러 버전을 건너뛰고 업데이트한 경우에는 사이의 버전을 묶어 보여 준다. 미디어는 가이드와 같은 smoke 캡처 파이프라인에서 나오므로 따로 관리할 필요가 없다.

작성은 T8 패키징과 묶는다. 릴리즈마다 `release-notes/<version>.ko.md`/`.en.md`(또는 항목·`guideId`·미디어 경로를 담은 JSON)를 두고, 앱에 번들해 **오프라인에서도** 열리게 한다. 초안은 이전 태그 이후의 Conventional Commits(`feat(scope): …`, 사용자에게 보이는 `fix`)를 스크립트로 모아 만들고, 사람이 3~5개로 줄여 다듬는다. 규칙 9가 이미 Conventional Commits를 요구하므로 추가 비용이 작다. `dictionary.ts`가 ko/en 누락 시 typecheck를 실패시키는 것처럼, 패키징 단계에서 해당 버전의 ko/en 노트가 없으면 빌드를 실패시킨다. electron-updater를 쓰면 다운로드 전 릴리즈 노트를 보여 줄 수도 있지만 **[추론]**, 이 모달은 "업데이트 이후 무엇이 달라졌나"를 앱 안에서 보여 주는 것이 목적이므로 별개로 둔다.

AI 트렌드 버튼과는 분명히 구분해야 한다. 트렌드 버튼은 **외부 소식**(Claude Code·Codex 릴리스, RSS, HN)을 네트워크에서 가져와 6시간마다 갱신한다. 릴리즈 노트는 **Aquila Agents 자신의 변화**를 앱에 번들해 버전이 바뀔 때만 보여 준다. 데이터 소스, 갱신 주기, 진입점(사이드바 상단 띠 버튼 대 `?` 메뉴와 업데이트 후 자동 표시)이 모두 다르다. 다만 목록 + 미디어 + 설명이라는 모양은 같으므로 모달 컴포넌트는 공유한다. 사용자가 두 기능을 헷갈리지 않도록 제목과 아이콘은 다르게 둔다("새로운 기능" / "AI 트렌드", "What's new" / "AI trends").

## 원격 머신 세션은 "UI는 로컬, 세션은 원격 tmux, 상태는 터미널 안으로"

> 오너 요구 사항: 프로젝트를 로컬과 원격 서버로 나눠서 열 수 있게. 근거: [notes/remote_sessions.md](notes/remote_sessions.md).

예전 `project.ssh`는 `ssh host claude`만 실행했다. 상태 점이 없었고(hook 없음), git 패널도 없었고, 연결이 끊기면 세션도 사라졌다. 그래서 제거됐다. 다시 넣으려면 비슷한 도구들이 수렴한 형태를 따르는 게 맞다. **UI는 로컬에 두고, 원격에서는 세션을 붙잡아 두는 프로세스가 돌며, 앱은 끊겼다가 다시 붙는다.** Zed, cmux, Wave, Claude 데스크톱 SSH 세션, VS Code Remote-SSH가 모두 이 구조다. 사용자 불만도 거의 한 가지다. 잠자기나 네트워크 끊김 뒤에 세션이나 터미널 내용을 잃는 것이다(VS Code Remote-SSH #1701, Claude 데스크톱 SSH 세션이 앱 재시작 후 복원되지 않는 문제 등). Claude Code 공식 문서도 원격에서는 `claude`를 tmux나 screen 안에서 띄우라고 권한다.

- **세션 유지는 전용 tmux 서버로.** `ssh -t <alias> -- tmux -L aquila new-session -A -s aq-<id> -c <path> -e CLAUDE_CONFIG_DIR=... '<cmd>'`. `-L aquila`는 별도 tmux 서버라 사용자의 tmux와 설정을 건드리지 않는다. `-A`는 "없으면 만들고 있으면 붙기"라서 재연결도 같은 명령이다. 환경변수는 SendEnv(서버의 AcceptEnv에 막히는 경우가 많다) 대신 명령에 직접 싣는다.
- **상태는 터미널 안으로(in-band).** OSC 7501, 9, 777은 pty를 타고 ssh를 그대로 지나온다. 로컬과 원격이 **같은 OSC 파서**를 쓰면 된다. 위 실측대로 Claude Code는 7501 질의에 응답만 해 주면 상태를 보낸다. Claude Code hook이 `terminalSequence`를 돌려주면 Claude가 그 OSC를 직접 쓰는 방법도 있다. tmux 3.3+는 `allow-passthrough on`이 없으면 이 시퀀스를 버리므로, 우리 전용 서버를 원격 `~/.aquila/tmux.conf`(사용자 rc 파일 아님)로 띄워 켠다 **[추론·검증 필요: 7501 질의/응답이 tmux를 왕복하는지]**. `ssh -R` 역방향 포워딩으로 hook을 받는 방식은 공유 서버에서의 포트 충돌·보안, 회사 서버의 `AllowTcpForwarding no`, 끊긴 동안의 이벤트 유실 문제가 있어 나중의 선택 채널로 둔다.
- **재연결.** ssh가 255로 끝나거나 Mac이 잠에서 깨면 3→6→12→최대 60초 백오프로 다시 붙는다(cmux 방식). `ServerAliveInterval=20`, `ServerAliveCountMax=2`를 넣는다. 앱을 다시 켜면 원격 tmux 세션 목록(`tmux -L aquila ls`)을 읽어 탭을 되살린다. T4(세션 복원)와 같은 모델로 묶는다.
- **설정과 보안.** 호스트는 사용자의 `~/.ssh/config`와 시스템 `ssh`·ssh-agent를 그대로 쓴다. 비밀은 저장하지 않는다. 처음 연결할 때 한 번 `uname`과 `claude`/`codex`/`tmux`/`git` 유무·로그인 상태를 확인하고, 없으면 설치 명령을 **안내만** 한다(자동 설치 안 함). 원격에서도 규칙 6이 그대로다. 원격 `~/.claude*`, `~/.codex`, rc 파일은 쓰지 않고, 우리 파일은 원격 `~/.aquila/` 아래에만 둔다. 원격 서버의 `systemd-logind KillUserProcesses=yes`는 SSH가 끊길 때 tmux까지 죽이므로 안내가 필요하다(Claude 데스크톱 문서).
- **UI.** 프로젝트마다 "실행 위치: 이 Mac / <호스트>"를 고른다. 사이드바에 호스트 배지와 연결 상태 점(연결됨 / 다시 연결 중 / 끊김, Wave의 Attached/Detached/Lost와 같은 구분)을 두고, 끊기면 세션 위에 배너를 띄운다.
- **패널은 다음 단계.** 원격 git 패널·히스토리·시스템 모니터는 같은 연결(ControlMaster 다중화) 위에서 `git`/`ps`를 돌린다. 지연은 아직 재지 않았다. Windows 기본 OpenSSH는 ControlMaster가 없어 따로 제어 채널이 필요하고, WSL은 원격보다 "로컬에 가까운" 대상으로 다룬다.

**MVP:** (1) `project.location = local | ssh{alias, path, claudeConfigDir}` (2) 전용 tmux로 실행·재접속 (3) 백오프 재연결과 앱 재시작 후 재부착 (4) OSC 파서 공유로 상태 표시, 안 되면 출력 휴리스틱 (5) 첫 연결 점검과 설치 안내 (6) 호스트 배지·연결 점·끊김 배너. **v1.1:** 원격 git·히스토리·모니터. **v1.2:** Windows. **v2:** 선택형 헬퍼 바이너리, mosh, tmux control mode(`-CC`).

### 권고: 상태 판정의 1차 경로를 OSC 7501로 옮긴다

확인 결과 가장 큰 변화는 이것이다. **Claude Code는 질의에 응답하는 터미널에만 OSC 7501을 보내고, Codex 0.169.1에도 OSC 7501 발신 코드가 있다.** 두 CLI 모두 hook이나 `-c` 주입 없이 `working`, `blocked`(+`kind=permission/question/auth`), `done`, `error`, `idle`을 직접 알려 준다는 뜻이다. 상태가 pty 스트림 안으로 오므로 규칙 6과 완전히 맞고, Windows에서 걸리던 셸 의존성(command hook)과 WSL 네트워킹 문제(hook 콜백 주소)도 상태 경로에서 빠진다. 그래서 #25를 "보조 신호"에서 **Now(최우선)**로 올린다.

1. **질의 응답을 먼저 구현한다.** pty 출력에서 `OSC 7501 ; ?`를 보면 `OSC 7501 ; ? : states=idle,working,done,blocked,error : kinds=permission,question,auth ST`로 답한다. **[추론]** 상태 판정을 main으로 옮기는 #19와 묶어 main에서 처리하면, 숨긴 탭의 렌더러 스로틀링과 상관없이 바로 답하고, xterm의 DA1 자동 응답보다 먼저 도착한다. 청크 경계에 걸친 시퀀스는 따로 버퍼링한다.
2. **Claude Code 2.1.295+ 세션은 OSC 7501을 상태의 근거로 삼는다.** probe에 응답했는데 보고가 오지 않는 구버전은 지금의 hook과 출력 휴리스틱으로 떨어진다.
3. **hook(#2·#3)은 알림 본문용으로 남긴다.** OSC 7501의 `msg`는 한 줄 설명뿐이다. `tool_name`/`tool_input` 요약과 `last_assistant_message`는 여전히 hook이 준다. `http` hook 전환의 가치는 줄지 않지만, 상태 정확도가 더는 hook에 달려 있지 않다.
4. **Codex는 스파이크 하나로 정한다.** Aquila pty에서 OSC 7501이 나오면 #24(OSC 9 알림 가로채기)는 필요 없다. 나오지 않으면 `-c tui.notifications=true -c tui.notification_method="osc9" -c tui.notification_condition="always"`를 폴백으로 쓴다. 감지 목록을 통과하려고 `TERM_PROGRAM`을 위장하는 것은 다른 기능을 깨뜨릴 수 있으므로 하지 않고, 필요하면 Codex에 이슈를 낸다.
5. **스펙 변경에 대비한다.** 아직 proposal(rev 0.4)이므로 모르는 키와 상태는 무시하고, 받은 원문을 디버그 로그에 남기고, 휴리스틱 폴백은 지우지 않는다.

## 결론

이번 조사가 바꾼 관점은 이렇다. Aquila Agents의 경쟁 상대는 더 이상 tmux나 iTerm2가 아니다. 같은 문제를 1st-party로 푸는 Claude Code 데스크톱과 Codex 앱이다. 그러니 이길 수 있는 지점은 "더 많은 기능"이 아니라 **1st-party가 구조적으로 못 하는 것**이다. 벤더 둘을 같은 상태 체계로 보기, 사용자 셸·체크아웃·설정을 그대로 쓰기, 그리고 CLI가 not planned로 닫은 빈틈 메우기(picker 이름·검색, dev server point-and-prompt, 계정별 사용량)다. 동시에 표준이 Aquila Agents 쪽으로 오고 있다는 점도 중요하다. Claude Code는 OSC 7501을 내보내고(질의에 응답하는 터미널에 한해), Codex 0.169.1도 같은 시퀀스를 내보내며, 임베드 호스트용 옵션이 늘었고, Codex도 hook을 정식화했다. 세션 단위 플래그(`--settings`, `--mcp-config`, env 주입)와 터미널 시퀀스만으로 대부분의 통합을 해낼 수 있다는 뜻이다. 그래서 규칙 6(사용자 CLI 설정 무수정)은 제약이 아니라 지속 가능한 아키텍처가 된다.

남은 불확실성은 대부분 Codex 쪽에 몰려 있다. `-c` 오버라이드로 hooks·MCP·알림을 세션 단위로 주입할 수 있느냐가 Codex 상태 판정, Figma 배선, 알림 품질을 한꺼번에 좌우한다. 첫 스파이크로 하루를 쓸 가치가 충분하다. 또 하나는 Aquila Agents 자신의 체력이다. WebGL 컨텍스트, xterm 5.5, 5초 폴링은 지금은 보이지 않지만 세션 15개를 넘는 파워 유저에게 먼저 드러날 결함이다. 상태와 알림을 고치는 것과 같은 "Now"에 넣어야 한다. Windows 요구는 순서를 한 번 더 바꾼다. 플랫폼 계층과 `http` hook은 Windows 기능이 아니라 **이후 모든 기능의 바닥**이다. 이 둘 없이 hook 확장, 상태 엔진, 시스템 모니터를 만들면 macOS 전용 코드를 두 번 쓰게 된다. 가이드와 릴리즈 노트는 smoke 캡처 파이프라인을 공유하므로, 처음부터 macOS와 Windows 두 러너에서 돌게 설계하면 크로스플랫폼 회귀를 잡는 장치도 함께 얻는다.
