# 편한 ADE는 주의력을 지켜 준다

개발자가 편하다고 느끼는 ADE의 핵심은 기능 수가 아니다. **사람의 주의력을 얼마나 아껴 주느냐**가 핵심이다. 2025–2026년 에세이와 제품 사례는 같은 결론을 낸다. 에이전트 병렬 실행에서 비싼 것은 컴퓨팅이 아니다. 사람의 감시, 컨텍스트 전환, 리뷰 비용이다. Addy Osmani는 이를 "ambient anxiety tax"라고 부르고 "More agents running doesn't mean more of you available."이라고 쓴다 ([Osmani](https://addyosmani.com/blog/cognitive-parallel-agents/)). 그래서 편한 ADE에는 공통 구조가 있다. 첫째, 항상 켜져 있지만 조용한 상태 표시층과 "내가 꼭 필요할 때만" 울리는 방해층을 나눈다. 둘째, 전환은 "나를 기다리는 세션으로 키 하나"로 끝난다. 셋째, 세션 이름·브랜치·마지막 메시지를 앱이 기억해 준다. 넷째, 상태 표시가 정직하다. 다섯째, 돌아왔을 때 "무엇이 바뀌었고 무엇을 결정해야 하는지"를 바로 보여 준다. Aquila Agents는 이미 이 구조의 상당 부분을 갖췄다. OSC 7501/hook 기반 상태 엔진, ⌘J "다음 대기 세션", 맥락이 담긴 알림, 대기 수만 세는 Dock 배지, 재실행 시 복원이 그 예다. 따라서 남은 과제는 새 기능보다 **조율**이다. "완료"를 덜 시끄럽게 만들고, 본 알림은 스스로 사라지게 하고, 세션 행을 더 알아보기 쉽게 하고, 조용히 하는 수단(quiet/mute)을 주고, macOS 관례를 지키는 것이다. 이 결론은 대부분 실무자 블로그, 벤더 문서, 커뮤니티 의견에 근거한다. 통제된 사용자 연구는 거의 없다는 점을 먼저 밝혀 둔다.

## 비싼 것은 감시 처리량이고, 연산 처리량이 아니다

ADE라는 용어는 2025년 6월 Warp 2.0이 스스로를 "the first Agentic Development Environment"라고 부르면서 자리 잡았다. 이 범주는 개발자를 직접 조작하는 사람(operator)에서 여러 에이전트를 조율하는 관리자로 옮겨 놓는다 ([Warp blog](https://www.warp.dev/blog/reimagining-coding-agentic-development-environment); [InfoWorld](https://www.infoworld.com/article/4193975/the-ide-is-dead-long-live-the-ade.html)). Osmani는 "the agent is the unit of work, not the file"이라고 정리하고, 핵심 패턴으로 **attention routing as a first-class event**, diff-first 리뷰, 거버넌스를 꼽는다 ([Osmani, Is the IDE dead?](https://addyosmani.com/blog/death-of-the-ide/)). 같은 저자의 "Orchestration Tax"에 따르면 에이전트를 띄우는 비용은 싸고 루프를 닫는 비용은 비싸다. 사람은 리뷰를 한 번에 하나씩만 할 수 있고, "바쁘다는 느낌"과 생산성은 겉보기에 구분되지 않는다 ([Osmani](https://addyosmani.com/blog/orchestration-tax/)).

실무 수치도 같은 방향이다. Osmani는 동시에 굴릴 수 있는 스레드를 보통 **3–4개**로 보고 "start with one thread fewer than feels right"라고 권한다. 스레드 하나는 약 **30분 안에 리뷰할 수 있어야** 한다. 피로의 원인은 능동적 사고보다 "background vigilance"이고, 전환 비용은 전환 자체보다 복귀에 드는 시간에 있다 ([Osmani](https://addyosmani.com/blog/cognitive-parallel-agents/)). 에이전트를 2개에서 약 12개로 늘려 본 한 실무자는 "Adding a third didn't add a third of the load, it multiplied it"라고 썼다. 자신이 스케줄러 역할을 떠맡았기 때문이다 ([Mergify](https://mergify.com/blog/how-agents-work-with-parallel-agents)). 반론도 있다. 한 에이전트를 기다리는 유휴 시간도 이미 컨텍스트 전환이니 병렬의 추가 비용은 작다는 의견이다 ([Edwin Burgers](https://nl.linkedin.com/in/edwinburgers)). 다만 근거가 개인 의견 수준이다. 3–4라는 숫자 역시 한 사람의 경험치일 뿐 측정된 값이 아니다.

이 프레임은 Aquila의 UX 판단 기준을 바꾼다. 좋은 변경은 패널이나 세션을 더 늘리는 변경이 아니다. **방해 횟수, 복귀 비용, "누가 나를 기다리나"를 확인하는 비용을 줄이는 변경**이다.

## 일곱 가지 UX 품질로 본 편안함

### 차분한 주의: 주변부는 늘 켜 두고, 방해는 자리를 비웠을 때만

편안한 도구들은 구조가 같다. Josh Morony는 tmux와 Claude hook으로 만든 워크플로에서 두 질문을 분리한다. "전체 상태가 어떤가?"는 한눈에 보는 상태 바가 맡고, "돌아가야 하나?"는 알림이 맡는다. 알림은 터미널이 앞에 있지 않을 때만 울리므로 "spammed while watching"이 없다. 돌아왔을 때도 알림은 남아 있고, 해당 인스턴스를 보면 스스로 철회된다. 그래서 "a pile of stale alerts to clear by hand"가 쌓이지 않는다 ([Morony workflow](https://www.joshmorony.com/workflows/handoff-claude-code-tmux-status-indicator/)). cmux는 에이전트가 사용자를 필요로 할 때만 pane에 파란 링을 두르고 탭을 밝힌다. 개발 동기는 Claude 기본 알림이 "always the same generic message"였다는 점이다 ([cmux README](https://raw.githubusercontent.com/manaflow-ai/cmux/HEAD/README.md)). Blake Crosley는 이를 "The queue should show attention, not activity"라고 요약하고 거짓 긴급성을 경계한다. "a failed lint check on a draft branch should not look like a production mismatch" ([Crosley](https://blakecrosley.com/blog/agents-need-supervision-surfaces)). Calm technology 원칙도 같은 말을 한다. "should make use of the periphery", "can communicate, but doesn't need to speak" ([calmtech.com](https://calmtech.com/)).

소음 불만은 거의 언제나 세 가지에서 나온다. 사용자가 이미 보고 있는데 울리는 신호, 일반적인 문구, 질문마다 반복되는 소리다. Ghostty는 Claude가 질문할 때마다 벨이 울려서 끄는 방법을 다룬 블로그 글이 따로 있다 ([andrewbaker.ninja](https://andrewbaker.ninja/2026/08/17/silencing-the-ghostty-bell-when-claude-code-asks-a-question/)). 창에 포커스가 있어도 배너가 뜬다는 불만도 있다 ([ghostty #10691](https://github.com/ghostty-org/ghostty/discussions/10691)). NN/g는 우선순위 없는 경보를 "alert fatigue"의 원인으로 지목하고 ([NN/g](https://www.nngroup.com/videos/alert-fatigue-user-interfaces/)), 알림을 줄였더니 만족도가 올랐다는 Facebook 사례도 실무 글에 자주 인용된다(2차 출처) ([MagicBell](https://magicbell.com/blog/help-your-users-avoid-notification-fatigue)).

**Aquila에의 함의.** Aquila는 이미 기반이 단단하다. 알림은 창이 포커스되지 않았거나 해당 세션이 활성이 아닐 때만 뜬다. 제목은 프로젝트와 브랜치, 본문은 `Claude · Needs input — Bash: npm install` 형식이다. 같은 상태는 30초 안에 반복 알림하지 않고, 400ms 동안 상태가 안정되기를 기다린다. Dock 배지는 `waiting` 수만 센다. 화면에 뜬 `done`은 `idle`로 바뀐다(`docs/en/ARCHITECTURE.md` "Attention"). 남은 간극은 네 가지다. 첫째, **`done`도 기본으로 시스템 알림을 띄운다.** 연구는 공통적으로 "완료는 기다릴 수 있으니 조용한 상태로, 방해는 permission/질문/에러에만"을 권한다. done 배너는 opt-in으로 돌리는 편이 맞다. 둘째, 알림 센터에 이미 전달된 알림을 세션을 열람할 때 **철회(retract)**하는 처리가 코드상 보이지 않는다. 셋째, "화면에 있음"이 포커스된 세션만 뜻한다(T15 잔여). 그래서 split 화면에 보이는 다른 pane도 알림을 띄운다. 넷째, 전역 quiet 토글과 세션·프로젝트 단위 mute가 없다. 조사한 도구 중 세션 단위 mute를 문서화한 곳도 없었으므로, 이것은 차별화 기회이기도 하다.

### 저마찰 전환: 훑지 말고 키 하나로 "나를 기다리는 곳"으로

전환이 편하다고 느끼는 조건은 세 가지다. 스캔 없이 기다리는 세션으로 바로 가고, 각 세션을 한눈에 알아보고, 다시 들어갔을 때 바로 맥락을 잡는 것이다. cmux는 가장 최근의 읽지 않은 알림으로 점프하는 단축키를 두고 ([cmux README](https://raw.githubusercontent.com/manaflow-ai/cmux/HEAD/README.md)), iTerm2는 **주의가 필요한 세션이 위로 오게 정렬한** 목록을 쓴다 ([iTerm2 docs](https://iterm2.com/claude-code-integration.html)). Claude Code 데스크톱 재설계(2026년 4월)는 여러 저장소의 세션을 사이드바 하나에 모으고 `⌘/`로 단축키를 보여 준다 ([Anthropic](https://claude.com/blog/claude-code-desktop-redesign)). 반대로 "Parallel Code" 작성자는 tmux가 고쳐 주는 것은 배치뿐이라며 "Layout is not workflow"라고 썼다 ([dev.to/johannesjo](https://dev.to/johannesjo/why-multitasking-with-ai-coding-agents-breaks-down-and-how-i-fixed-it-2lm0)). Cursor 2.0이 에이전트 중심 레이아웃으로 크게 바뀌자 "2.0 – a step in the wrong direction", "Lost in New UIs" 같은 스레드가 줄을 이었다. **사용자의 랜드마크를 옮기는 일**은 그만큼 비싸다 ([Cursor forum](https://forum.cursor.com/t/2-0-a-step-in-the-wrong-direction/139648?page=5)).

키보드 측면에서는 Superhuman의 command palette 원칙이 기준점이다. 어디서나 동작하는 단축키 하나를 쓰고, 다시 누르면 닫히며 이전 포커스로 돌아간다. 퍼지 매칭으로 "lnik"이 "link"를 찾는다. 사용자가 제품 용어를 모를 수 있으니 동의어를 넣는다. 결과마다 단축키를 함께 보여 줘서 "learn the shortcut for next time"이 가능하게 한다 ([Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/)).

**Aquila에의 함의.** ⌘J는 waiting > error > done 순서로 순환하고, 같은 단계 안에서는 가장 오래 기다린 세션이 먼저다. ⌘K palette도 urgency 순으로 정렬한다. 이것은 조사한 제품 대부분보다 앞선 설계다(Conductor, Codex app, Claude desktop에서는 같은 단축키를 찾지 못했다). 남은 일은 다듬기다. palette에 동의어를 넣는다("new/spawn/start/run/열기" → 세션 열기). palette 단축키는 다시 누르면 닫히도록 한다. pty가 Ctrl/Option 키를 대부분 쓰므로 앱 단축키는 ⌘에만 둔다. 무엇보다 지금의 사이드바·탭·패널 배치를 **안정된 랜드마크로 지킨다.**

### 낮은 기억 부담: 앱이 기억하고, 사용자는 알아보기만

전환의 절반은 "어느 탭이 뭐였지?"를 떠올리는 비용이다. 모든 Ghostty 탭 제목이 "Claude Code"로 똑같았던 사례 ([dev.to](https://dev.to/liran_baba/why-every-ghostty-tab-said-claude-code-and-the-30-line-zsh-hook-that-fixed-it-19h5)), Claude 스피너가 pane 제목을 덮어쓴다는 이슈 ([issue #55397](https://claudeissues.com/issue/55397-feature-include-session-name-in-terminal-title-critical-for-tmux-cc-iterm2)), 세션 이름 붙이기 요청 ([issue #36909](https://claudeissues.com/issue/36909-feature-request-session-naming-and-machine-readable-state-indicators-for-multi-s))이 모두 같은 증상이다. 해법은 풍부한 행(row)이다. cmux 탭은 브랜치, PR 상태, cwd, 포트, 최근 알림 문구를 보여 주고 ([cmux README](https://raw.githubusercontent.com/manaflow-ai/cmux/HEAD/README.md)), VS Code 세션 행은 상태와 변경 통계를 보여 준다 ([VS Code docs](https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions)). 재시작을 넘는 기억도 중요하다. Superset은 앱을 종료하거나 업데이트해도 세션이 "stay alive and running"이라고 내세운다 ([Show HN: Superset](https://hn.svelte.dev/item/46368739)). 사용자들은 `claude /resume`이 자동으로 되지 않아서 직접 스크립트를 짠다 ([classmethod](https://dev.classmethod.jp/en/articles/cmux-auto-resume-claude-code/)). Arc 사용자들이 Spaces를 칭찬하면서도 고정 탭이 재시작 후 사라지면 크게 불평한 것도 같은 맥락이다 ([dev.to Arc review](https://dev.to/pickuma/arc-browser-review-18-months-with-a-browser-that-thinks-differently-26o1)). NN/g의 progressive disclosure 원칙도 함께 볼 만하다. 기본 화면은 단순하게 두고 고급 기능은 한 단계 뒤에 둔다 ([NN/g](https://www.nngroup.com/articles/progressive-disclosure/)).

**Aquila에의 함의.** Restore v2가 탭, 레이아웃, 포커스, scrollback을 복원하고 Claude/Codex resume을 시도한다. 사용자들이 가장 많이 직접 스크립트로 짜던 고통을 이미 없앴다는 뜻이다. 다음 단계는 **사이드바 행의 인지성**이다. 사용자가 고칠 수 있고 CLI가 덮어쓰지 못하는 세션 제목을 둔다(현재 rename은 프로젝트에만 있다). 또 이미 파싱해 둔 `last_assistant_message` 첫 줄이나 permission 요약을 행의 보조 줄로 보여 준다. 그러면 알림을 놓쳤어도 사이드바만 보고 상태를 파악할 수 있다. 복원되었지만 아직 실행 중이 아닌 세션(dormant)은 살아 있는 것처럼 보이지 않게 구분해야 한다.

### 신뢰와 통제: 틀린 점보다 "모름"이 낫다

사용자가 통제감을 느끼는 조건은 셋이다. 막힌 순간이 이유와 함께 분명히 보이고, 피해 반경이 격리되어 있고(worktree/container), 자율 수준을 직접 고를 수 있어야 한다 ([Warp blog](https://www.warp.dev/blog/reimagining-coding-agentic-development-environment); [Conductor](https://www.conductor.build/)). 신뢰를 가장 빨리 깎는 것은 **조용히 고장 나는 상태 표시**다. Claude가 `~/.claude/settings.json`을 다시 쓰면서 iTerm2의 hook이 빠지면, 탭이 아무 경고 없이 갱신을 멈춘다 ([agentsroom](https://agentsroom.dev/blog/claude-code-in-iterm2-what-the-integration-does)). Linear의 Agent Interaction Guidelines는 에이전트가 자기 내부 상태에 대해 "clear and transparent"해야 한다고 하고, 세션 상태를 waiting for input / working / completed / errored 네 가지로 줄인다. 또 "an agent that keeps going after being told to stop erodes trust faster than one that makes mistakes"라고 경고한다 ([Linear AIG](https://linear.app/developers/aig); [Linear](https://linear.app/now/our-approach-to-building-the-agent-interaction-sdk)). 확인 대화상자는 NN/g 기준을 따르면 된다. 되돌릴 수 없는 일에만 쓰고, 결과를 구체적으로 말하고, Yes/No 대신 "Stop & close" 같은 동작 라벨을 붙인다. "if you cry wolf too many times, people will stop paying attention" ([NN/g](https://www.nngroup.com/articles/confirmation-dialog/)). 가능하면 확인보다 undo가 낫다 ([Matuschak](https://notes.andymatuschak.org/zXH4ASvHNz488hCNgrBjQJK)).

**Aquila에의 함의.** Aquila의 상태 엔진은 이 영역의 모범 답안에 가깝다. 신뢰도 순서(OSC 7501 > hook > 키 입력 > 출력 활동 > 종료 코드)가 정해져 있고, 휴리스틱 "done"은 `estimated`로 흐리게 표시하고, Esc/Ctrl+C는 즉시 `stopped`로 반영한다. 사용자 전역 설정을 건드리지 않고 `--settings ~/.aquila/claude-hooks.json`으로 세션마다 주입하므로 iTerm2식 취약성도 없다. 이 점은 숨기지 말고 **신뢰의 근거로 드러낼 만하다**. 보강할 점도 있다. hook이나 7501 신호가 한동안 끊겼을 때는 "상태 알 수 없음"을 보여 줘야 한다. 조사한 어떤 제품도 이 상황을 문서화하지 않았다. 작업 중인 세션을 닫을 때는 구체적인 확인을 쓰고, 유휴 세션이면 확인 없이 닫는다. 사이드바에서 프로젝트를 빼는 것처럼 되돌릴 수 있는 동작에는 확인 대신 undo 토스트를 쓴다. Permission UI는 CLI의 것이므로 Aquila가 따로 만들지 않는다. 대신 그 프롬프트를 **빨리 찾게** 해 주는 것이 Aquila의 역할이다.

### 리뷰와 인계: 돌아온 순간이 가장 비싸다

모든 출처가 꼽는 병목은 리뷰다. Superset HN 스레드는 "typing time"이 "reading time"으로 바뀌었다고 표현한다 ([Show HN: Superset](https://hn.svelte.dev/item/46368739)). 요리하면서 Sculptor로 앱 대부분을 만든 사용자는 리뷰할 때 "the diffs, Sculptor's internal to-do list, and summaries"가 도움이 됐다고 했다 ([Show HN: Sculptor](https://hn.svelte.dev/item/45427697)). VS Code Inbox mode는 세션을 보관하지 않고 "acknowledge"만 하는 명시적인 "봤음" 동작을 둔다. 새 활동이 오면 세션이 다시 위로 올라온다 ([VS Code docs](https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions)). Osmani는 리뷰를 몰아서 하고, 테스트나 스크린샷 같은 기계적 증거를 붙이고, "마지막으로 읽은 이후 바뀐 것"을 추적해서 "cognitive debt"를 피하라고 권한다(그의 논지를 정리한 것) ([Osmani](https://addyosmani.com/blog/orchestration-tax/)). Crosley는 "Recovery belongs beside the failed event"라고 쓴다. 실패한 곳 바로 옆에 재시도·재개·되돌리기를 두라는 뜻이다 ([Crosley](https://blakecrosley.com/blog/agents-need-supervision-surfaces)).

**Aquila에의 함의.** Changes panel v2(watch + review loop)가 이미 diff-first 리뷰를 앱 안에서 처리한다. 편안함을 더하는 마지막 조각은 **"마지막으로 본 이후"** 표시다. 세션 행과 Changes panel에 마지막 포커스 이후 생긴 출력이나 변경을 표시해 주면, 복귀 비용이 "처음부터 다시 읽기"에서 "새로 생긴 것만 읽기"로 줄어든다. pty가 비정상 종료하면 전역 토스트 대신 그 pane 안에 "같은 cwd에서 다시 열기"를 바로 둔다.

### 온보딩: 길을 막지 않는 첫 화면

NN/g는 walkthrough 튜토리얼이 "dramatically overused"되어 있다고 말한다. "paradox of the active user" 때문에 사람들은 바로 일을 시작하려 하고, 맥락 밖에서 본 안내는 기억하지 못한다 ([NN/g](https://www.nngroup.com/articles/onboarding-tutorials/)). 복잡한 앱의 빈 상태는 시스템 상태를 알리고, 핵심 작업으로 가는 직접 경로를 주는 자리다 ([NN/g](https://nngroup.com/articles/empty-state-interface-design)). 실제 사례로 Warp는 강제 로그인과 설문 때문에 "why does a terminal app need an account?"라는 불만을 가장 많이 받았고, 결국 로그인을 선택 사항으로 바꿨다 ([dev.to](https://dev.to/krunchdata/warp-a-terminal-behind-login-popup-5284); [Warp blog](https://warp.dev/blog/open-source-and-login-for-warp)).

**Aquila에의 함의.** First-run 체크리스트는 이 기준에 맞는다. 계정이 필요 없고, 설치되지 않은 CLI에는 복사 가능한 설치 명령을 보여 주고, 선택 항목은 기본이 Skip이다. 가이드는 "Take a tour / Skip"으로 제안만 한다. 남은 개선은 **맥락 안에서 가르치기**다. 처음으로 세션이 입력을 기다릴 때 "⌘J로 기다리는 세션으로 이동"을 한 번만 보여 주는 식이다. 또 T17 잔여로 남은 "사이드바에 폴더를 드롭해서 프로젝트 추가"를 채운다.

### 속도와 네이티브 감각: 400ms와 macOS 관례

Doherty threshold는 "Provide system feedback within 400 ms"를 기준으로 삼는다 ([Laws of UX](https://lawsofux.com/doherty-threshold/)). Linear가 빠르게 느껴지는 이유는 낙관적 업데이트와 키보드 우선 설계에 있다고 분석된다. "Users perceive speed based on how quickly the interface reacts"([performance.dev](https://performance.dev/how-is-linear-so-fast-a-technical-breakdown), 코드를 보지 않은 제3자 분석). Electron 앱에 대한 불만은 성능보다 **OS 관례 위반**에 몰린다. 시스템 단축키가 제대로 안 먹고, 날짜 형식이 지역 설정을 무시하고, 메모리와 CPU를 과하게 쓴다는 것이다. 반면 VS Code 사용자는 "that it's an Electron app"이라는 사실을 잊는다고 한다 ([Michael Tsai](https://mjtsai.com/blog/2025/04/25/is-electron-really-that-bad)). Raycast가 표준 macOS 컨트롤 대신 커스텀 컴포넌트를 만든 사례를 보면, 네이티브 감각은 위젯 모양보다 **행동**의 문제다 ([Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast.md)).

**Aquila에의 함의.** 성능 쪽은 측정으로 확인됐다. T16에서 세션 15개 기준 CPU 2.8%, 120fps, Ctrl+C 응답 21ms를 기록했고, 배터리 프로필도 있다. 가장 눈에 띄는 네이티브 간극은 **앱 메뉴 바가 아직 없다는 것**이다(T13 잔여). 표준 메뉴(About, Settings… ⌘,, Hide ⌘H, Window, ⌘M, 전체 화면)와 단축키 표기는 Mac 사용자가 기대하는 발견성을 공짜로 준다. 또 Electron 앱의 대표적 불만인 시스템 단축키 충돌도 줄여 준다. 세션 열기는 탭과 "starting…" 상태를 즉시 보여 준 뒤 pty를 붙여서, UI가 spawn을 기다리며 멈추지 않게 해야 한다.

## Conclusion

이번 조사에서 가장 크게 바뀐 관점은 이것이다. Aquila의 다음 UX 과제는 "무엇을 더 보여 줄까"가 아니라 **"무엇을 덜 말할까"**다. 상태 엔진, ⌘J, 맥락 알림, 복원처럼 주의 라우팅의 골격은 이미 조사한 상용 제품 대부분과 같거나 앞서 있다. 반면 편안함을 깎는 요소는 대개 "조금 과한 말하기"에서 나온다. done 배너, 철회되지 않는 알림, 보이는 split pane에서 울리는 알림, 끌 수 없는 소리가 그렇다. 이런 것들은 고치는 비용이 작고, 하루에도 수십 번 체감된다. 그래서 우선순위 상단에 두었다.

불확실성도 남아 있다. 몇 개의 병렬 세션이 편한지, 알림 피로가 개발 도구에서 얼마나 측정 가능한지에 대한 통제 연구는 없다. 근거 대부분은 2025–2026년 실무자 경험이다. 따라서 위 원칙은 정답 목록이 아니라 검증할 가설로 다뤄야 한다. 알림 클릭률, ⌘J 사용 빈도, 알림을 끄는 비율 같은 앱 내부 신호로 확인해 나가는 것이 다음 단계다. 세션 단위 mute와 "상태 알 수 없음" 표시는 조사한 어떤 제품도 문서화하지 않은 빈자리다. 이 둘은 Aquila가 "정직하고 조용한 ADE"로 자리 잡을 수 있는 구체적인 지점이다.
