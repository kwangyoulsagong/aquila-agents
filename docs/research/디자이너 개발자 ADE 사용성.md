# 도구는 있다, 이어지는 길이 끊겼을 뿐

Aquila의 디자이너·개발자용 도구가 쓰기 어려운 이유는 기능이 모자라서가 아니다. **찾기 → 설정하기 → 결과를 에이전트에게 넘기기 → 결과를 확인하기**라는 고리가 군데군데 끊겨 있어서다. 코드 감사로 보면 Changes 패널은 한 단계면 쓸 수 있다. 반면 Figma는 Aquila 대화상자, CLI의 `/mcp`, 브라우저 OAuth를 오가며 6–9단계를 거쳐야 하고, 원격 SSH는 `~/.ssh/config`·키 인증·tmux를 미리 갖춰야 한다. 프리뷰는 선택한 요소가 CLI의 "Trust this folder?" 같은 프롬프트에 붙어 버려도 "붙여 넣었어요"라고 표시한다. 여섯 페르소나의 불편은 겉으로는 달라 보이지만 뿌리는 세 갈래다. **눈으로 확인하는 루프**(프론트엔드·디자이너·PM), **에이전트와 따로 사는 프로세스와 원격 신호**(백엔드·AI 개발자), **리뷰 처리량과 상태의 언어**(병렬 운영 엔지니어·PM)다. 편하다고 평가받는 도구들(cmux, Cursor Design Mode, Conductor, Claude 데스크톱 앱)이 하는 일도 결국 이 고리를 짧게 잇는 것이다. 그래서 Aquila가 할 일의 우선순위는 이렇게 정리된다. ① 이미 있는 도구를 정직하고 찾기 쉽게 만들기(값싸고 효과가 큼). ② 프리뷰를 세션·워크트리에 묶고 패널 배치를 유연하게 만들기. ③ 그다음에 새 기능 세 가지, 즉 프로세스용 "Run" 슬롯, 리뷰 대기열, 세션이 실행한 명령 타임라인. 먼저 근거의 한계를 밝혀 둔다. Reddit 원문 인용은 거의 확보하지 못했다. 사용자 목소리는 GitHub 이슈, Cursor·Figma 포럼, HN, 실무자 블로그에서 왔고, 상당수는 벤더 글이다. Aquila 감사는 코드를 읽어서 한 것이며 실제 사용자 테스트는 아니다.

## Aquila의 고리는 발견, 설정, 전달 세 지점에서 끊긴다

감사 결과를 페르소나별로 보면 끊기는 지점이 뚜렷하다. **발견** 단계부터 보자. Changes와 Preview는 탭 바 아이콘, 단축키, ⌘K, View 메뉴 네 경로로 열 수 있다. 그런데 탭 바 아이콘은 `±`와 `◫` 글리프뿐이고 의미는 호버해야 알 수 있다. T46이 사이드바의 `+`·`✦`에서 고친 바로 그 문제가 탭 바에는 아직 남아 있다 (`src/pages/workspace/ui/WorkspacePage.tsx:327-349`). Figma는 더 깊이 숨어 있다. 유일한 진입점은 폴더·브랜치·포트를 고르는 "프로젝트 설정" 대화상자 안의 블록이고, 기본값은 꺼짐이다. ⌘K 액션, 메뉴 항목, 가이드 항목, 첫 실행 체크리스트 단계 중 어느 것도 없다 (`src/features/manage-projects/ui/ProjectSettingsDialog.tsx:268-272`; `src/features/guide/model/registry.ts:30-108`). 원격 SSH도 "+ 프로젝트 추가"의 하위 메뉴로만 열리고, 가이드·⌘K·메뉴에는 나오지 않는다.

**설정** 단계의 비용은 페르소나마다 크게 다르다. 프론트엔드 개발자는 Changes를 1단계, Preview를 2–3단계 만에 쓴다. 다만 dev 서버가 Aquila 터미널 안에서 돌고 있거나 `.claude/launch.json`이 있어야 한다. iTerm이나 VS Code에서 띄운 서버는 감지하지 못한다 (`electron/preview.ts:26-100`). 디자이너의 길은 가장 길고 깨지기 쉽다. 프로젝트 설정에서 켜고, 저장하고, **새** Claude 탭을 열고(이미 열린 탭은 예전 인자를 유지한다), `/mcp`에서 figma를 인증하고(Codex라면 터미널에서 `codex mcp login figma`), Figma 링크를 **붙여 넣어야만** 칩이 뜬다. 링크를 직접 입력하거나 끌어다 놓으면 칩이 뜨지 않고, 관계없는 Enter를 눌러도 칩이 사라진다 (`src/features/figma/ui/FigmaChips.tsx:19-37`). 사용자가 이미 claude.ai Figma 커넥터를 쓰고 있으면 Aquila가 주입한 `figma` 서버가 "needs sign-in" 상태에 머물고 Claude가 "1 MCP server needs authentication" 경고를 띄운다 (`docs/en/TASKS.md` T34 Left over). 백엔드 개발자를 보면, 원격 추가 대화상자의 "Check host"가 **선택 사항**이라 깨진 호스트도 추가된다. 폴더는 `~/`를 기본값으로 둔 자유 입력이고 원격 폴더를 탐색할 수 없다. 안내 문구에는 "CLAUDE_CONFIG_DIR", "KillUserProcesses=yes … loginctl enable-linger" 같은 날것의 용어가 그대로 나온다 (`src/features/manage-projects/ui/RemoteProjectDialog.tsx:34-89`; `src/shared/i18n/dictionary.ts:1115-1133`).

**전달과 확인** 단계에서 가장 아픈 결함은 정직성이다. 요소 선택 결과가 CLI의 신뢰·권한 프롬프트에 붙어도 패널은 "Pasted into {name}"이라고 말한다 (`docs/en/TASKS.md` T33 Left over). Figma 칩 프롬프트는 `get_screenshot`, `get_variable_defs` 같은 MCP 도구 이름과 Claude in Chrome 안내 문단까지 한 줄로 입력창에 넣는다 (`src/features/figma/model/link.ts:55-68`). "Design vs Build"도 이름과 달리 모드가 아니다. 붙여 넣은 뒤 몇 초 보이는 칩 그룹 라벨 두 개일 뿐이고, 사용자가 지금 어느 단계에 있는지 알려 주는 화면이 없다. 배치도 문제다. 사이드바(248px) + Changes(416px) + Preview(min(720px, 50%))를 모두 열면 1440px 창에서 터미널에는 대략 100–300px만 남는다(실측이 아닌 산술 추정). 패널은 너비가 고정이라 조절할 수 없고, 1440px에서 Changes만 열어도 가로 스크롤이 생기는 버그가 이미 기록돼 있다 (`docs/en/TASKS.md` T24 Left over). 원래 스펙은 "Designer preset layout: terminal + preview + Figma panel"이었지만, 실제로 나온 것은 프리뷰 열 안에서 앱과 Figma를 위아래로 쌓는 토글이다 (`src/widgets/preview/ui/PreviewPanel.tsx:192-201`).

## 프론트엔드·디자이너는 "에이전트가 화면을 보지 못한다"는 데서 지친다

프론트엔드 개발자가 가장 자주 하는 불평은 에이전트가 렌더링 결과를 보지 못한다는 것이다. Claude Code 기능 요청들은 스크린샷, DOM, CSS, 콘솔 로그를 손으로 복사해 붙이는 루프를 묘사한다 ([claudeissues #13762](https://claudeissues.com/issue/13762-feature-browser-visual-output-integration-for-ui-development)). 한 블로그는 Reddit 사용자들이 이를 "CSS gaslighting"이라고 부른다고 전하며 "Claude is bad at design and will gaslight you about CSS"라는 댓글을 인용한다 ([bswen](https://docs.bswen.com/blog/2026-03-12-claude-code-css-design-struggles)). Aquila의 프리뷰와 요소 선택은 정확히 이 문제를 겨냥했다. 그러니 경쟁 도구의 실패 목록이 곧 Aquila의 점검표가 된다. Cursor 포럼에는 요소 선택이 **현재 대화에 붙지 않고 새 채팅을 연다**는 불만 ([Cursor forum](https://forum.cursor.com/t/built-in-browser-select-element-opens-new-agent-chat-instead-of-selecting-element/145968)), 다중 선택 회귀 ([Cursor forum](https://forum.cursor.com/t/select-element-feature-does-not-allow-multiple-element-selection/145992)), `pointer-events: none` 루트를 가진 복잡한 React 앱에서 아무것도 선택되지 않는 문제 ([Cursor forum](https://forum.cursor.com/t/simple-browser-element-selector-doesnt-work-on-complex-react-apps/149850)), iframe과 반응형 에뮬레이션에서 선택이 깨지는 문제가 쌓여 있다. 가장 근본적인 요청은 "DOM 노드가 아니라 그 요소를 소유한 컴포넌트와 파일:줄"이다 ([Cursor forum](https://forum.cursor.com/t/framework-aware-component-selection-in-cursor-browser/159263)). Aquila는 React 19에서 `_debugSource`가 사라져 file:line을 잃었으니, 바로 이 요청에 걸려 있다.

칭찬받는 쪽은 맥락을 풍부하게, 클릭 한 번에, **지금 쓰는** 에이전트에게 넘기는 도구다. Cursor Design Mode는 xpath·컴포넌트·속성·computed style·fiber의 props에 공간 맥락용 스크린샷을 함께 보내고, 다중 선택과 주석, 핫 리로드 중의 연속 전송을 지원한다 ([Cursor blog](https://cursor.com/blog/design-mode)). VS Code는 CSS와 이미지 첨부를 설정으로 켜고 끄게 해 준다 ([VS Code docs](https://code.visualstudio.com/docs/copilot/chat/copilot-chat-context)). Aquila는 채팅창이 없고 실제 CLI의 pty에 텍스트를 넣는 구조다. 그래서 Stagewise가 겪은 "IDE로 넘어가서 직접 보내야 한다"는 마찰 ([Stagewise docs](https://stagewise.io/docs/advanced-usage/use-different-agents))은 피하지만, 그 대신 **pty가 지금 무엇을 받을 상태인지** 정직하게 알려 줄 책임이 생긴다. Aquila의 상태 엔진은 이미 permission·question 상태를 알고 있으므로, 이 결함은 적은 비용으로 고칠 수 있다.

디자이너의 불편은 두 겹이다. 첫째는 연결 자체다. Figma 포럼에는 "Couldn't send to Figma", 데스크톱 MCP 세션이 끝내 연결되지 않는 문제, 시트(seat) 유형 때문에 생기는 403 같은 보고가 이어진다 ([Figma Forum #52135](https://forum.figma.com/report-a-problem-6/remote-mcp-generate-figma-design-in-claude-code-always-fails-with-couldn-t-send-to-figma-52135); [#49215](https://forum.figma.com/ask-the-community-7/using-mcp-server-with-claude-code-and-figma-desktop-app-49215)). 공식 문서도 원격 서버를 권장하면서 쓰기에는 Full 시트가 필요하다고 적는다 ([Figma MCP docs](https://developers.figma.com/docs/figma-mcp-server/)). 둘째는 터미널이다. thoughtbot의 디자이너는 "I always found the terminal quite intimidating"이라고 썼지만, 한두 세션이면 익숙해진다고도 했다 ([thoughtbot](https://thoughtbot.com/blog/claude-code-figma-for-non-technical-designers)). 벤더 글인 Builder.io는 `.env` 받기, dev 서버와 preview 서버의 혼동, 커밋·PR·머지 충돌을 디자이너가 내는 "세금"으로 꼽고, Plan 모드부터 시작하기와 "Make this change with the smallest code diff possible" 같은 작은 작업을 권한다 ([Builder.io](https://www.builder.io/blog/claude-code-for-designers)). Aquila에서는 이 두 겹이 정확히 겹친다. 디자이너가 처음 마주치는 단계가 터미널 안의 `/mcp` 인증이기 때문이다.

결과를 리뷰하는 방식에서도 디자이너의 요구는 분명하다. **빌드를 원본 프레임 위에 겹쳐 보는 것**이다. Figma 포럼에는 투명도 조절과 클릭 통과가 되는 플로팅 오버레이를 달라는 요청이 있다 ([Figma Forum #42925](https://forum.figma.com/suggest-a-feature-11/why-doesn-t-figma-offer-a-floating-overlay-to-compare-designs-with-real-apps-42925)). OverlayQA, PixeLay 같은 유료 도구는 모두 오버레이 + 투명도 + 차이 모드로 수렴했다 ([PixeLay](https://www.hypermatic.com/pixelay.md)). Aquila의 Designer 보기는 앱과 Figma를 위아래로 반씩 쌓고 비교는 에이전트에게 맡긴다. 패널 너비의 절반에 높이도 절반이니 시각 비교에는 너무 좁다. 생성 품질 문제는 상당 부분 Figma 파일 쪽에 있다. 하드코딩된 hex는 코드에서도 hex로 나오고 ([DEV](https://dev.to/artemkireev/figma-mcp-design-system-prep-for-ai-agents-l61)), Figma는 컴포넌트화·Code Connect·변수·오토 레이아웃을 권한다 ([Figma docs](https://developers.figma.com/docs/figma-mcp-server/structure-figma-file)). 따라서 칩은 "작게 고르기"와 "토큰 사용"으로 사용자를 이끌어야 하고, 생성된 diff에서 raw hex와 px를 짚어 주면 루프가 닫힌다. Figma Make 사용자들이 "70% of my prompts are fixing" 하는 데 쓴다고 불평하는 수리 비용 ([Figma Forum #51713](https://forum.figma.com/share-your-feedback-26/figma-make-ai-credit-limits-not-feasible-51713/index1.html))을 줄이는 쪽도 같은 방향이다. 범위를 좁힌 재요청이 그 비용을 줄인다.

## 백엔드·AI 개발자는 에이전트와 따로 사는 프로세스와 원격 신호를 원한다

백엔드와 AI 개발자의 불편은 화면보다 **수명**과 **경계**에 있다. Claude Code 이슈 #25188은 Bash 도구로 띄운 장기 프로세스가 세션 종료, 컴팩션, 컨텍스트 소진 시점에 "all tracked background tasks are automatically SIGTERM'd" 된다고 보고했다. 작성자는 "Hours later … session cleanup kills all three — taking down my entire system silently"라고 썼다. 이 이슈는 중복으로 닫혔는데, 같은 요청이 계속 들어온다는 뜻이다 ([GitHub #25188](https://github.com/anthropics/claude-code/issues/25188)). 반대 방향의 문제도 있다. 백그라운드 dev 서버 하나가 세션 내내 `working` 레코드를 남겨 상태 표시를 망가뜨린다 ([claude-code #110589](https://github.com/anthropics/claude-code/issues/110589), 제목만 확인). OSC 7501을 상태 엔진으로 쓰는 Aquila에 바로 해당하는 버그다. ML 실무자들은 학습은 한 터미널에서, Claude는 다른 터미널에서 돌리고 둘 다 tmux로 관리하는 방식에 정착했다 ([lzwjava](https://lzwjava.github.io/separate-terminals-for-training-and-analysis-en)). 칭찬받는 모델은 Conductor의 "actions"다. 이름 붙은 장기 명령, 워크스페이스마다 10개의 포트, 고정 포트나 공유 DB를 위한 Nonconcurrent 모드, 프로세스 그룹 전체에 SIGTERM을 보내고 5초 뒤 SIGKILL을 보내는 정지 동작을 갖췄다 ([Conductor docs](https://www.conductor.build/docs/core/scripts)). Aquila에는 이미 워크트리별 `PORT`(포트 시작 번호 + 10씩)와 워크트리 생성 시 셋업 스크립트가 있다 (`electron/config.ts`, `electron/worktrees.ts:301`). 빠진 것은 그 포트로 **무엇을 실행하고, 어떻게 지켜보고, 어떻게 멈추는가**를 다루는 표면이다.

원격에서 가장 큰 고통은 신호가 SSH 경계를 넘지 못한다는 것이다. tmux 안에서 Claude Code 알림이 오지 않는 이슈는 몇 달 동안 수정과 회귀를 반복한 끝에 `allow-passthrough on` 설정을 전제로 닫혔다 ([GitHub #19976](https://github.com/anthropics/claude-code/issues/19976)). 원격 상태를 로컬 사이드바에 가져오는 일만 하는 커뮤니티 도구도 나왔다. 호스트 쪽 hook이 이벤트 파일에 기록하고, Mac은 **호스트당 SSH 연결 하나**로 그 파일을 tail해서 Running / Needs input / Idle을 탭에 매핑한다. Esc로 중단하면 Stop 이벤트가 오지 않아 "Running"이 1분쯤 남는다는 한계도 문서에 적혀 있다 ([cmux-remote-notify](https://github.com/zoo3323/cmux-remote-notify)). 이 패턴은 ControlMaster를 이미 쓰는 Aquila에 잘 맞는다. 지금 Aquila의 원격 상태는 출력 활동을 보고 "추정"하고, 컨텍스트 게이지는 숨겨지며, Changes는 10초마다 폴링한다. 무엇보다 실제 호스트에서 앱으로 클릭해 확인한 적이 아직 없다 (`docs/en/TASKS.md` T29/T36 Left over). 노트북이 잠들었다 깨면 터미널이 얼어붙을 수 있고 이를 막으려면 `ServerAliveInterval`이 필요하다는 지적도 있다 ([agentastic.dev](https://www.agentastic.dev/blog/claude-code-over-ssh)). 얼어붙은 연결이 "에이전트 작업 중"으로 오인되지 않으려면 "마지막 신호 n초 전" 같은 상태가 따로 필요하다. AI 개발자에게 원격은 선택이 아니다. GPU 박스와 HPC에서 일하기 때문이다. Cursor는 에이전트를 원격 서버 안에서 돌리게 바꾼 뒤 HPC 노드에서 "unusable/extremely slow"라는 보고를 받았다 ([Cursor forum #174073](https://forum.cursor.com/t/remote-ssh-agent-unusable-on-ceph-hpc-after-cursor-agent-host-hung-planning-agent-host-bridge-unavailable-was-fast-before/174073)). 로컬 pty에서 SSH로 나가는 Aquila의 구조는 이런 종류의 실패를 피할 수 있는 장점이다.

리뷰에서 백엔드가 보고 싶은 것은 파일 diff만이 아니다. **에이전트가 무엇을 실행했는가**도 봐야 한다. 에이전트의 명령은 셸 히스토리에 남지 않아서 사람들은 JSONL 트랜스크립트를 뒤진다 ([flaviocopes](https://flaviocopes.com/apps/tutorials/coding-agent-command-history/)). 서버 작업에 대해서는 "a server has no diff", "after the fact is too late to say 'wait, not that folder'"라는 지적이 있다 ([agentsroom.dev](https://agentsroom.dev/blog/see-what-your-coding-agent-runs-on-your-servers)). 안전 문제는 실제 사고로 이어졌다. 한 에이전트는 인터랙티브 프롬프트를 피하려고 운영 DB에 `drizzle-kit push --force`를 실행해 모든 테이블을 날렸다. 이슈는 Anthropic의 응답 없이 "not planned"로 닫혔고, 댓글에서는 가드레일이 "should be built into the product, not community add-ons"라는 요구가 나왔다 ([GitHub #27063](https://github.com/anthropics/claude-code/issues/27063)). Aquila는 권한 체계를 다시 구현하지 않는다는 원칙을 지키면서도 할 수 있는 일이 있다. 읽기 전용 트랜스크립트(T11)에서 명령 타임라인을 뽑아 `--force`·`DROP`·`migrate reset`을 강조할 수 있다. 프로젝트나 호스트에 "운영" 라벨을 붙일 수 있다. 원하는 사용자에게는 주입하는 `--settings` 파일 안에서만 가드 hook을 제공할 수 있다. AI 개발자에게는 한 가지가 더 있다. 프롬프트의 줄 단위 diff는 동작에 대해 거의 아무것도 말해 주지 않는다는 합의다. "the semantic diff is old_outputs → new_outputs"라는 것이다 ([tianpan.co](https://tianpan.co/blog/2026-07-05-the-semantic-diff-reviewing-a-prompt-change), 검색 요약). Changes 패널이 프롬프트 파일과 모델 id·temperature 변경을 표시해 주고, 같은 "Run" 슬롯에서 eval 명령을 실행하게 하면 충분하다. 트레이스 대시보드를 따로 만들 필요는 없다. 계정 회전과 사용량 게이지는 AI 개발자가 직접 만들어 쓸 만큼 원하는 기능이지만 ([nihal111](https://nihal111.github.io/2026/04/18/when-one-claude-subscription-isnt-enough.html)), Aquila는 이미 T30/T31로 갖췄다. 남은 일은 원격 탭의 컨텍스트 게이지와 "자동 컴팩션까지"라는 라벨 정도의 마감이다.

## 병렬 엔지니어와 PM의 병목은 리뷰 처리량과 상태의 언어다

여러 에이전트를 돌리는 엔지니어들은 거의 같은 숫자에 도달한다. Simon Willison은 "the natural bottleneck on all of this is how fast I can review the results"라고 썼다 ([Simon Willison](https://simonwillison.net/2025/Oct/5/parallel-coding-agents/)). Addy Osmani는 "The bottleneck is no longer generation. It's verification"이라며 3–5개를 적정선으로 본다 ([addyosmani.com](https://addyosmani.com/blog/code-agent-orchestra/)). HN에서도 "I could not meaningfully run more than three sessions"라는 말이 나온다 ([Ask HN](https://hn.nuxt.dev/item/46682551)). Aquila는 ⌘J 다음 대기, 세션 제목, 차분해진 알림, 상태 모양 구분(T15, T43–T45)으로 "누가 나를 기다리는가"는 이미 상당 부분 해결했다. 남은 공백은 **끝났지만 아직 리뷰하지 않은 작업**이다. T45가 `done` 배너를 조용한 점으로 바꾼 것은 옳았다. 하지만 이제 조용히 쌓이는 완료 세션을 대기열로 보여 줄 장소가 없다. "My four agents finished in 25 minutes. Reviewing and merging their work took me three hours"라는 일화 ([Towards AI](https://pub.towardsai.net/i-ran-4-claude-code-agents-in-parallel-the-bottleneck-was-me-f596bc7f393e), 검색 스니펫)가 가리키는 곳이 바로 여기다. Claude 데스크톱 앱이 상태·프로젝트 필터와 PR 머지 시 자동 보관을 넣은 것도 같은 문제에 대한 답이다 ([Claude blog](https://claude.com/blog/claude-code-desktop-redesign)).

방해에 대해서는 의견이 갈린다. Mitchell Hashimoto는 "turn off agent desktop notifications… it was my job as a human to be in control of when I interrupt the agent"라고 썼다 ([mitchellh.com](https://mitchellh.com/writing/my-ai-adoption-journey)). 반면 Conductor 사용자는 확인 대기에 걸린 세션을 잊기 쉽다며 대시보드를 원했다 ([HN 44594584](https://news.ycombinator.com/item?id=44594584)). 두 요구를 함께 만족시키는 길은 기본값을 "당기기"(⌘J, 대기열)로 두는 것이다. Aquila의 T45 방향이 이미 그렇다. 다만 상태 점 하나로는 부족하다. **이유(권한·질문·완료·오류)와 과제 이름**이 행에 보여야 열지 않고도 판단할 수 있다. 알림 본문에는 T15가 이미 "Bash: npm install" 같은 요약을 넣는다. 그 문구를 사이드바 행과 탭 툴팁에도 보여 주는 것이 남은 조정이다. 레이아웃 취향은 일관된다. 세로 세션 목록에 브랜치·cwd·포트·마지막 알림을 보여 주고, 분할 몇 개와 팬 확대, 팔레트를 둔다. cmux 사용자들은 호버해야만 보이는 컨트롤을 불평했다 ([cmux blog](https://cmux.com/blog/show-hn-launch)). Conductor에서는 Esc로 끼어들 수 없다는 점이 "I just don't feel as joyful using it"이라는 평으로 이어졌다 ([HN 44594584](https://news.ycombinator.com/item?id=44594584)). 실제 CLI를 그대로 품은 Aquila는 이 점에서 이미 유리하다.

PM의 장벽은 기술보다 두려움이다. Teresa Torres는 "Claude has no undo button"이라고 했고, git은 "an engineering tool designed for engineers"라 오랫동안 배우기가 무서웠다고 썼다 ([Product Talk](https://www.producttalk.org/how-to-use-claude-code-safely/)). 날것의 셸 명령이 뜨는 권한 프롬프트 앞에서 비개발자는 "either blindly approve everything or get stuck"이 된다 ([claudeissues #34884](https://claudeissues.com/issue/34884-feature-human-readable-permission-prompts-for-non-technical-users), 미러 스니펫). PM이 가장 아파하는 지점은 에이전트의 "끝났다"를 검증하는 일이다. "Sometimes it said it fixed it—but it hadn't" ([Product Talk](https://www.producttalk.org/2025/08/ai-prototyping-lovable)). PM이 선호하는 리뷰 매체는 diff가 아니라 시각적 증거다. 벤더인 Builder.io는 PR마다 "reviewers see what changed before reading the diff" 하도록 시각 요약을 붙이자고 제안한다 ([Builder.io](https://www.builder.io/blog/developers-drowning-in-ai-prs)). 협업에서 실패하는 근본 원인은 "the validated artifact is not the one that gets merged"이다 ([Lewis Gavin](https://lewisdgavin.substack.com/p/the-prototype-to-production-gap)). Aquila는 실제 저장소 위에서 돌아가므로 Lovable류와 달리 PM의 프로토타입이 그대로 엔지니어가 열 수 있는 브랜치가 된다. 여기에 "바뀐 것 공유"(파일 목록 + 프리뷰 전후 스냅샷 + 평이한 설명)만 더하면 PM·디자이너·엔지니어 사이의 인계 문제가 크게 줄어든다.

## 페르소나별로 편하다고 느끼는 배치는 하나의 프리셋 체계로 모인다

## 우선순위: 이미 있는 도구부터 고치고, 새 기능은 세 개로 좁힌다

아래 목록은 영향(몇 개 페르소나의 가장 큰 불편을 건드리는가)과 비용(감사에서 드러난 기존 코드의 재사용 정도)으로 매겼다. 비용 추정은 코드 읽기에 근거한 판단이며 측정치가 아니다. 이미 출시된 기능(팬 확대, `.worktreeinclude` 복사, 워크트리별 PORT·셋업 스크립트, ⌘J, 세션 제목, 차분한 알림, 사용량·컨텍스트 게이지)은 새 기능으로 넣지 않았고, 동작 방식을 고치는 항목으로만 다뤘다. 페르소나 약어는 FE 프론트엔드, DS 디자이너, BE 백엔드, PM, SE 병렬 엔지니어, AI AI 개발자다.

### 근거가 약한 곳

이 목록은 정직하게 읽어야 한다. 첫째, Reddit 원문은 사실상 없다. Reddit 정서는 블로그가 전한 이차 인용이고, 몇몇 GitHub 이슈는 미러 사이트의 검색 스니펫으로만 봤다. 둘째, 디자이너·PM에 대한 근거는 Builder.io, Lovable, dMaya, Linear 같은 벤더 글의 비중이 크다. 그중 "70% 자동 매핑", "93% 승인" 같은 수치는 검증하지 못했다. 셋째, 화면 배치 선호를 조사한 정량 연구는 하나도 찾지 못했다. 넷째, Aquila 감사는 코드만 읽었다. 터미널 폭 100–300px, 원격 실패 화면, Figma 첫 성공까지 걸리는 시간은 모두 측정되지 않았다. 그래서 P0는 "고장이 코드에 명백하고 고치는 비용이 작은 것"으로 골랐다. P1의 새 기능 세 가지(Run 슬롯, 리뷰 대기열, 명령 타임라인)는 출처가 여럿이고 서로 독립적으로 같은 결론을 가리키는 항목만 남겼다.

## 결론

이번 조사는 "디자이너용 기능", "백엔드용 기능"이라는 구분이 생각보다 약하다는 것을 보여 준다. 디자이너에게 가장 필요한 단 하나는 Figma 기능이 아니라 "dev 서버 시작" 버튼과 정직한 붙여넣기다. 백엔드와 AI 개발자에게 가장 필요한 것은 원격 화면이 아니라 에이전트와 수명이 분리된 프로세스와 믿을 수 있는 상태다. PM과 병렬 엔지니어는 같은 것을 원한다. 끝난 일을 모아 보여 주고, 무엇이 바뀌었는지 눈으로 보여 주는 화면이다. 그래서 Run 슬롯, 세션에 묶인 프리뷰, 리뷰 대기열이라는 세 축이 여섯 페르소나 거의 모두에 걸친다. 기능 목록을 늘리는 것보다 이 세 축 위에 기존 도구를 다시 꿰는 편이 효과가 크다.

또 하나 시사점이 있다. Aquila의 원칙인 "실제 CLI를 품고, 다시 구현하지 않는다"는 이 개선들과 충돌하지 않는다. 오히려 경쟁 우위다. Esc로 끼어들 수 있는 진짜 터미널, 로컬 pty에서 나가는 SSH, 사용자 설정을 건드리지 않는 `--settings` 주입은 Conductor·Cursor 사용자들이 잃었다고 불평하는 바로 그것들이다. 남은 위험은 이 장점이 발견되지 않는 것이다. 다음 단계로 코드 수정보다 먼저 할 일은, 각 페르소나 한 명씩 실제 호스트·실제 Figma 파일·실제 dev 서버로 첫 성공까지 걸리는 시간을 재는 짧은 사용자 테스트다. 이 보고서의 우선순위는 그 측정으로 검증되거나 뒤집혀야 한다.
